Я переглянув твої скриншоти `TASKTRACKER.V_TASKS_FULL_2` і логіку формування `creator_info_html`.

Твоя пропозиція правильна, але я б дещо змінив архітектуру SQL, щоб вона коректно працювала не лише з двома користувачами на першому етапі, а й з будь-якою їх кількістю.

Головна зміна: інформацію про того, хто видав завдання, потрібно визначати не за записами `SIGNATURERIGHTS`, а за фактичною останньою відміткою в `SIGNATUREHISTORY`, пов'язаною з правами першого етапу (`stages_id = 2`).

## 1. Як має працювати нова логіка

Я пропоную залишити існуючий формат відображення в Interactive Report, але змінити джерело інформації для блоку «Видано».

| Ситуація                                | Що відображаємо                                                    |
| --------------------------------------- | ------------------------------------------------------------------ |
| Завдання створене, відміток немає       | Створено: автор + дата                                             |
| Автор сам поставив відмітку             | Створено: автор + дата; Видано: дата                               |
| Відмітку поставив керівник              | Створено: автор + дата; Видано: керівник + дата                    |
| Автор поставив відмітку, потім керівник | Створено: автор + дата; Видано: керівник + дата останньої відмітки |
| Кілька керівників поставили відмітки    | Виводимо останнього, хто поставив відмітку, та її дату             |

Наприклад:

До появи відміток

Створено: Іваненко І. П. — начальник відділу

01.11.2026 09:00

Після відмітки керівника

Створено: Іваненко І. П. — начальник відділу

01.11.2026 09:00

Видано: Петренко О. М. — директор департаменту

01.11.2026 10:35

Тут важливий нюанс: якщо автор сам видав завдання, можна, як у твоїй поточній реалізації, не дублювати його ПІБ і посаду, а показати тільки «Видано» та дату.

## 2. Що вже є у твоєму SQL

Зі скриншотів видно, що ти вже створив CTE `creator_sign`, який вибирає дані з `TaskTracker.SIGNATUREHISTORY`:

```
ROW_NUMBER() OVER (
    PARTITION BY h.signright_id
    ORDER BY h.sdate DESC, h.id DESC
) AS rn
```

А потім приєднуєш:

```
LEFT JOIN creator_sign cs
    ON cs.signright_id = sr.id
   AND cs.rn = 1
```

Це правильна основа, але є проблема.

Зараз ти визначаєш останню відмітку окремо для кожного `signright_id`, а потрібно визначати останню відмітку серед усіх `SIGNATURERIGHTS` першого етапу конкретного завдання.

Наприклад, якщо є три користувачі:

| signright_id | Користувач | Час відмітки |
| ------------ | ---------- | ------------ |
| 101          | Автор      | 09:15        |
| 102          | Керівник   | 10:20        |
| 103          | Заступник  | 10:45        |

Поточний `ROW_NUMBER()` може повернути три записи з `rn = 1` — по одному для кожного права.

Потім `MAX(...) KEEP (DENSE_RANK FIRST ORDER BY stages_id, sort_order, sr_id)` обирає інформацію відповідно до порядку `SIGNATURERIGHTS`, а не за часом фактичного підписання.

Саме тому остання відмітка керівника може не потрапити до `creator_info_html`.

## 3. Як я рекомендую переробити SQL

Я б залишив CTE `creator_sign`, оскільки він уже формує історичні ПІБ, посади та підрозділи. Але додав би окремий CTE, який визначатиме останню фактичну відмітку для завдання.

### Крок 1. Залишаємо `creator_sign`

Твій наявний `creator_sign` можна поки не змінювати. Він уже правильно використовує:

```
COALESCE(pos_hist.name, us.spr_dolznost)
    AS signer_dolznost,

COALESCE(dep_hist.short_name, us.tseh_short)
    AS signer_tseh_short
```

Це корисно, адже дозволяє показати посаду й підрозділ працівника на момент підписання, якщо збережено відповідний історичний знімок.

### Крок 2. Додаємо CTE `creator_last_sign`

Одразу після `creator_sign` додай:

```
creator_last_sign AS (
    SELECT
        task_id,
        signright_id,
        signer_by,
        signer_date
    FROM (
        SELECT
            sr.task_id,
            h.signright_id,
            h.signer_by,
            h.signer_date,

            ROW_NUMBER() OVER (
                PARTITION BY sr.task_id
                ORDER BY
                    h.sdate DESC NULLS LAST,
                    h.id DESC
            ) AS rn

        FROM TaskTracker.SIGNATURERIGHTS sr

        JOIN TaskTracker.SIGNATUREHISTORY h
            ON h.signright_id = sr.id

        WHERE sr.stages_id = 2
          AND h.signer_date IS NOT NULL
    )
    WHERE rn = 1
),
```

Тепер ми отримуємо тільки один запис для кожного `task_id`, незалежно від кількості користувачів першого етапу.

Важливо: я використав `h.sdate` як критерій хронології, тому що саме він використовується у твоєму поточному `creator_sign`. Якщо фактичний час відмітки визначається полем `signer_date`, сортувати потрібно за ним. Також я припускаю, що заповнений `signer_date` означає завершену відмітку, а не лише створення запису історії.

### Крок 3. Приєднуємо останню відмітку до `creator_info`

У CTE `creator_info` замість:

```
LEFT JOIN creator_sign cs
    ON cs.signright_id = sr.id
   AND cs.rn = 1
```

використай:

```
LEFT JOIN creator_last_sign cls
    ON cls.task_id = sr.task_id

LEFT JOIN creator_sign cs
    ON cs.signright_id = cls.signright_id
   AND cs.rn = 1
```

Тут `cls` визначає останню відмітку, а `cs` надає інформацію про користувача з історії.

Проте цього недостатньо: у поточному `creator_info` ще є вибір рядка через `KEEP (DENSE_RANK FIRST ...)`, тому його теж потрібно скоригувати.

### Крок 4. Змінюємо вибір у `creator_info`

Зараз у тебе:

```
MAX(creator_info_html) KEEP (
    DENSE_RANK FIRST
    ORDER BY stages_id, sort_order, sr_id
) AS creator_info_html
```

Оскільки `creator_last_sign` уже визначив потрібного користувача для всього завдання, вибір за `sort_order` більше не повинен впливати на те, хто вважається останнім підписантом.

У фінальному варіанті я рекомендую формувати `creator_info_html` з одного рядка на завдання, а не створювати кілька HTML-рядків і вибирати один із них через `KEEP`.

Для цього інформацію про автора потрібно брати з основного запису завдання, а інформацію про видачу — з `creator_last_sign` і `creator_sign`.

## 4. Умови для блоку «Видано»

У твоєму поточному SQL є складний вкладений `CASE`, який порівнює `cs.signer_by` та `sr.user_tabno`.

Я рекомендую спростити його до трьох ситуацій:

```
CASE
    -- Відмітки ще немає
    WHEN cls.signright_id IS NULL THEN
        NULL

    -- Завдання видав сам автор
    WHEN cs.signer_by = creator_user_tabno THEN
        '<br /><span class="signer_info">' ||
        '<span class="exctr-ttl">Видано:</span> ' ||
        TO_CHAR(
            cls.signer_date,
            'DD.MM.YYYY HH24:MI'
        ) ||
        '</span>'

    -- Завдання видав інший користувач
    ELSE
        '<br /><span class="signer_info">' ||
        '<span class="exctr-ttl">Видано:</span><br />' ||

        cs.signer_familia || ' ' ||
        SUBSTR(cs.signer_imya, 1, 1) || '. ' ||
        SUBSTR(cs.signer_otchestvo, 1, 1) || '. ' ||

        NVL(cs.signer_dolznost, '') || ' ' ||
        NVL(cs.signer_tseh_short, '') || ' ' ||

        TO_CHAR(
            cls.signer_date,
            'DD.MM.YYYY HH24:MI'
        ) ||
        '</span>'
END
```

Тут `creator_user_tabno` — умовна назва поля з табельним номером автора завдання. Її потрібно замінити фактичним полем із твоєї View. Не варто використовувати `sr.user_tabno` для порівняння з автором, оскільки `sr` описує учасника етапу, а не обов'язково автора.

Також у твоїй View потрібно зберегти окрему логіку для випадку, коли `SIGNATURERIGHTS.USER_TABNO` порожній, оскільки, судячи зі скриншотів, ти підтримуєш і рольову модель підписання.

## 5. Ще один важливий момент — продуктивність Oracle 21

Оскільки `V_TASKS_FULL_2` використовується в APEX Interactive Report, я б уникав багаторазового обчислення історії підписів для кожного рядка.

Для великої кількості завдань варто перевірити індекси:

```
-- Для пошуку прав першого етапу
CREATE INDEX IX_SR_STAGE_TASK
ON TaskTracker.SIGNATURERIGHTS
    (STAGES_ID, TASK_ID, ID);

-- Для пошуку історії за правом
CREATE INDEX IX_SH_RIGHT_DATE
ON TaskTracker.SIGNATUREHISTORY
    (SIGNRIGHT_ID, SDATE DESC, ID DESC);
```

Це лише кандидати на індекси: перед створенням потрібно перевірити наявні індекси, обсяг таблиць і план виконання. Зокрема, індекс за `SIGNRIGHT_ID` може вже існувати.

## 6. Що я б зробив у твоєму проєкті

Моя рекомендація — не змінювати принцип відображення `creator_info_html`, а розділити відповідальність за визначення автора та особи, яка фактично видала завдання.

- Автор завдання визначається один раз із даних самого завдання.
- Останній підписант визначається з `SIGNATUREHISTORY` серед усіх прав `SIGNATURERIGHTS` першого етапу.
- ПІБ, посада та підрозділ підписанта беруться з історичного знімка, якщо він є.
- HTML формується лише після визначення цих даних.

Також я б не прив'язував логіку до того, що останній підписант обов'язково є керівником. Якщо останню відмітку поставив автор після керівника, система за твоїм правилом покаже автора. Якщо ж бізнес-логіка вимагає завжди показувати саме керівника, це вже інше правило вибору.

Щоб я міг підготувати тобі повністю готовий SQL без умовних назв колонок, надішли текст View `V_TASKS_FULL_2` у форматі `.sql` або `.txt`.

Тоді я зможу переробити безпосередньо `creator_sign` і `creator_info`, зберігши твої наявні HTML-класи, історичні посади, підтримку рольових підписів і всі інші колонки View.
