Так. Запропонована архітектура RBAC + ABAC + Scope дозволяє реалізувати всі п’ять сценаріїв. Причому для цього не потрібно створювати окрему роль для кожного підрозділу, типу схеми або комбінації прав.

Для твого проєкту «Альбом схем» (Next.js + Konva + Zustand + Node.js API + Oracle 21) я рекомендую будувати доступ навколо трьох незалежних параметрів:

- Роль — що користувач може робити (`reader`, `editor`, `administrator`).
- Область доступу (Scope) — з якими схемами він може працювати (всі схеми, конкретний підрозділ, unit, альбом або схема).
- Тип схеми — до яких категорій належать дозволи (`equipment`, `building` тощо).

Розглянемо твої сценарії.

## 1. Різні права для схем обладнання та будівель

Це реалізується через призначення ролі разом із типом схеми.

| Користувач | Роль   | Тип схеми | Область      |
| ---------- | ------ | --------- | ------------ |
| User 101   | reader | equipment | Усі          |
| User 102   | reader | building  | Усі          |
| User 103   | reader | equipment | Усі          |
| User 103   | reader | building  | Усі          |
| User 104   | editor | equipment | Підрозділ 10 |

У результаті:

- User 101 бачить лише схеми обладнання.
- User 102 бачить лише схеми будівель.
- User 103 бачить обидва типи.
- User 104 редагує схеми обладнання підрозділу 10.

Для User 103 можна також створити один запис із типом `ALL`, якщо така семантика підтримується твоєю моделлю призначень.

Важливо: `equipment` і `building` повинні бути значеннями поля типу схеми в БД, а не окремими ролями на кшталт `equipment_reader`.

## 2. Обмеження за підрозділом та unit

Також повністю підтримується.

Припустимо, організаційна структура виглядає так:

Підприємство

Підрозділ 10

Unit 101

Unit 102

Підрозділ 20

Unit 201

Unit 202

Тут важливо, щоб кожна схема мала чітку організаційну належність.

Наприклад:

```
const scheme = {
  id: 500,
  name: "Схема обладнання насосної станції",
  schemeType: "equipment",
  divisionId: 10,
  unitId: 101,
  createdBy: 125
};
```

Тоді редактор підрозділу 10 може редагувати схеми підрозділу 10, включно з unit 101 та 102, якщо його призначення поширюється на дочірні unit.

Редактор unit 101 — лише схеми цього unit.

### Чи потрібно враховувати автора?

Я не рекомендую обмежувати редагування лише автором схеми.

Для технічних схем це створить проблеми: автор може змінити посаду, перейти в інший підрозділ або звільнитися, але схеми повинні залишатися доступними для актуалізації.

Краще розділити:

- `createdBy` — хто створив схему.
- `updatedBy` — хто востаннє редагував.
- `divisionId` і `unitId` — кому схема належить.
- `scheme.edit` — хто має право її змінювати.

Таким чином усі редактори відповідного підрозділу зможуть працювати зі схемою незалежно від автора.

## 3. Перегляд усіх схем, але редагування тільки своїх

Це один із найважливіших сценаріїв, і він реалізується дуже просто — двома незалежними призначеннями ролей.

Користувач 125

2 призначення

reader

Тип: усі схеми

Область: усе підприємство

editor

Тип: equipment

Область: підрозділ 10

Результат:

| Схема                    | Перегляд | Редагування |
| ------------------------ | -------- | ----------- |
| Обладнання підрозділу 10 |          |             |
| Обладнання підрозділу 20 |          |             |
| Будівля підрозділу 10    |          |             |
| Будівля підрозділу 20    |          |             |

Це працюватиме і з кнопками «Переглянути» та «Редагувати», про які ми говорили раніше.

## 4. Зв'язки між схемами різних підрозділів

Тут я підтримую твою ідею: для більшості користувачів варто забезпечити глобальний перегляд схем, залишивши редагування обмеженим.

Наприклад, користувач відкриває схему електропостачання підрозділу 10. На ній є об'єкт, який посилається на схему підрозділу 20.

Схема А

Підрозділ 10

Схема Б

Підрозділ 20

Перехід за зв'язком між схемами

Якщо користувач має глобальний `reader`, він безперешкодно перейде зі схеми А до схеми Б.

Якщо він має `editor` лише для підрозділу 10, то:

- Схема А відкриється в режимі редагування, якщо він його вибере.
- Схема Б відкриється лише для перегляду.
- Навіть якщо користувач змінить URL на `?mode=editor`, редагування схеми Б буде заборонено.

Є ще один важливий нюанс: доступ до схеми не повинен автоматично надавати доступ до всіх пов'язаних із нею файлів або конфіденційних параметрів. Для вкладень та чутливих даних можна згодом додати окремі дозволи.

## 5. Додаткові сценарії

Ось ще кілька корисних комбінацій, які підтримує така модель.

| Сценарій                      | Призначення                                |
| ----------------------------- | ------------------------------------------ |
| Інженер підрозділу            | `reader` GLOBAL + `editor` DIVISION        |
| Начальник unit                | `reader` GLOBAL + `editor` UNIT            |
| Фахівець із будівель          | `reader` GLOBAL + `editor` BUILDING        |
| Головний інженер підприємства | `reader` GLOBAL + `editor` GLOBAL          |
| Зовнішній аудитор             | `reader` для конкретного альбому           |
| Проєктна група                | `editor` для конкретних схем або альбому   |
| Адміністратор підрозділу      | `administrator` DIVISION + `reader` GLOBAL |
| Тимчасовий виконавець         | `editor` SCHEME з датою завершення доступу |

Для тимчасових дозволів достатньо передбачити `VALID_FROM` і `VALID_TO` у таблиці призначень.

## 6. Як саме система визначатиме доступ

Кожне призначення ролі перевіряється окремо, а дозволи об'єднуються.

Не можна брати глобальний Scope від `reader` та комбінувати його з правом редагування від `editor`. Це випадково дозволило б користувачу редагувати всі схеми підприємства.

Ось спрощений алгоритм:

```
function canAccess(user, permission, scheme) {
  return user.assignments.some((assignment) => {
    if (!assignment.active) return false;

    if (!roleHasPermission(
      assignment.role,
      permission
    )) {
      return false;
    }

    if (!matchesSchemeType(
      assignment,
      scheme
    )) {
      return false;
    }

    return matchesScope(assignment, scheme);
  });
}
```

Функції `roleHasPermission`, `matchesSchemeType` і `matchesScope` — окремі частини реалізації політики доступів. На сервері вони мають використовувати актуальні призначення з БД, а не довіряти даним із браузера.

## 7. Що я рекомендую остаточно закласти в Oracle 21

У таблиці `ACCESS_ASSIGNMENT` мають бути щонайменше такі поля:

| Поле             | Призначення                           |
| ---------------- | ------------------------------------- |
| `USER_ID`        | Кому видано роль                      |
| `ROLE_ID`        | Яку роль видано                       |
| `SCOPE_TYPE`     | GLOBAL, DIVISION, UNIT, ALBUM, SCHEME |
| `SCOPE_ID`       | Ідентифікатор конкретної області      |
| `SCHEME_TYPE_ID` | Тип схеми або NULL для всіх типів     |
| `VALID_FROM`     | Початок дії                           |
| `VALID_TO`       | Завершення дії                        |
| `REVOKED_AT`     | Дата відкликання                      |
| `GRANTED_BY`     | Хто надав роль                        |

Тут я рекомендую `SCHEME_TYPE_ID` зробити зовнішнім ключем на окремий довідник типів схем. Це дозволить додавати нові типи без зміни коду ролей.

Також потрібно визначити правила ієрархії `DIVISION → UNIT` і поведінку для схем, які належать одразу кільком організаційним одиницям. Якщо така ситуація можлива, одних `DIVISION_ID` та `UNIT_ID` у схемі буде недостатньо — знадобиться окрема таблиця належності схем.

## Моя рекомендація для «Альбому схем»

Я б вибрав таку базову політику:

За замовчуванням: усі авторизовані користувачі, яким призначено глобальну роль `reader`, можуть переглядати всі звичайні схеми підприємства та переходити між пов'язаними схемами.

Редагування: надається окремими призначеннями `editor` з обмеженням за типом схеми, підрозділом, unit або конкретним альбомом.

Адміністрування: окремий дозвіл, який не означає автоматичного права редагувати схеми.

Авторство: використовується для історії змін, але не визначає право редагування.

Ця модель добре масштабується і не вимагатиме додавати нові ролі щоразу, коли з'явиться новий підрозділ, тип схеми або посада.

Єдине, що я рекомендую перевірити перед остаточним впровадженням: чи підтримують підготовлені раніше SQL-таблиці та API всі п'ять рівнів Scope (`GLOBAL`, `DIVISION`, `UNIT`, `ALBUM`, `SCHEME`) і фільтрацію за типом схеми. Якщо ні, потрібно доповнити їх до впровадження сторінки адміністратора, щоб не переробляти механізм видачі ролей пізніше.
