У твоїй системі редактора схем обладнання таблиця `DOC_OBJECT_LINK` відповідає за зв'язки між об'єктами всередині конкретної версії документа.

Це важлива таблиця, оскільки в тебе є не лише `nodes` (обладнання) та `edges` (лінії), а й ЗВТ, відгалуження, точки підключення та інші об'єкти, які можуть бути пов'язані між собою.

Однак тут є принциповий нюанс: `DOC_OBJECT_LINK` не повинна дублювати всі лінії, які вже зберігаються як EDGE у `DOC_OBJECT`. Вона має зберігати інформацію про те, які саме об'єкти з'єднані та яким способом.

## 1. Різниця між DOC_OBJECT та DOC_OBJECT_LINK

Уявімо просту схему обладнання:

Насос з'єднаний із клапаном за допомогою лінії EDGE-001.

У `DOC_OBJECT` будуть три записи:

| OBJECT_ID | OBJECT_TYPE | LABEL       |
| --------- | ----------- | ----------- |
| NODE-001  | NODE        | Насос       |
| NODE-002  | NODE        | Клапан      |
| EDGE-001  | EDGE        | Трубопровід |

Тобто `DOC_OBJECT` відповідає на запитання: які об'єкти існують на схемі?

А `DOC_OBJECT_LINK` відповідає на інше запитання: які об'єкти пов'язані між собою?

Наприклад:

| SOURCE_OBJECT_ID | TARGET_OBJECT_ID | LINK_TYPE      |
| ---------------- | ---------------- | -------------- |
| EDGE-001         | NODE-001         | START_ATTACHED |
| EDGE-001         | NODE-002         | END_ATTACHED   |

Тут ми фіксуємо, що початок лінії підключений до насоса, а кінець — до клапана.

Це один із можливих способів моделювання. Він особливо зручний для твого редактора, де EDGE має власний ID, геометрію, точки зламу й інші властивості.

## 2. Що означають поля DOC_OBJECT_LINK

За структурою, яку ми раніше розглядали:

| Поле               | Призначення                                                              |
| ------------------ | ------------------------------------------------------------------------ |
| `LINK_ID`          | Унікальний ID запису зв'язку                                             |
| `DOC_VERSION_ID`   | Версія документа, у якій існує зв'язок                                   |
| `SOURCE_OBJECT_ID` | Об'єкт, від якого визначено зв'язок                                      |
| `TARGET_OBJECT_ID` | Об'єкт, до якого визначено зв'язок                                       |
| `LINK_TYPE`        | Тип зв'язку                                                              |
| `SOURCE_ANCHOR`    | Точка підключення на вихідному об'єкті                                   |
| `TARGET_ANCHOR`    | Точка підключення на цільовому об'єкті                                   |
| `SEGMENT_ID`       | Ідентифікатор сегмента, якщо зв'язок стосується конкретної частини лінії |

Не всі поля обов'язково використовувати для кожного типу зв'язку. Наприклад, `SEGMENT_ID` може бути `NULL`.

## 3. Як це співвідноситься з твоїм Zustand Store

На попередніх скріншотах у тебе EDGE має приблизно таку структуру:

```
{
  id: "edge-001",
  kind: "connector",
  connectorType: "orthogonal-elbow",

  start: {
    x: 100,
    y: 150,
    attached: {
      // інформація про підключення
    }
  },

  end: {
    x: 400,
    y: 150,
    attached: {
      // інформація про підключення
    }
  },

  points: [...],
  route: {...},
  geometry: {...},
  segmentsMeta: [...]
}
```

Тут потрібно розділити дві групи інформації.

Геометрія EDGE: `points`, `route`, `geometry`, `segmentsMeta`, координати та стиль. Вона потрібна для відтворення лінії на Canvas і залишається в JSON Snapshot.

Логічні підключення EDGE: `start.attached` і `end.attached`, якщо вони містять посилання на інші об'єкти. Саме з них можна формувати записи в `DOC_OBJECT_LINK`.

Наприклад, якщо `start.attached` вказує на `node-001`, а `end.attached` — на `node-002`, API може сформувати два записи зв'язків.

Але я поки не бачив повної структури `attached` у твоєму Store. Тому не варто писати код, який припускає, що там обов'язково є поле `nodeId`. Спочатку треба перевірити фактичну модель.

## 4. Навіщо взагалі потрібна ця таблиця, якщо вже є JSON?

Це ключове архітектурне питання.

JSON уже містить інформацію про всю схему. Теоретично ти можеш відкрити JSON, пройтися по масиву `edges` і знайти, до яких вузлів підключена лінія.

Але уявімо, що в тебе тисячі схем і потрібно знайти всі об'єкти, безпосередньо підключені до конкретного насоса.

Без `DOC_OBJECT_LINK` доведеться аналізувати JSON кожної схеми або використовувати складні JSON-запити.

З індексованими зв'язками це простий SQL:

```
SELECT
    l.LINK_TYPE,
    l.SOURCE_OBJECT_ID,
    l.TARGET_OBJECT_ID,
    o.OBJECT_TYPE,
    o.LABEL
FROM DOC_OBJECT_LINK l
JOIN DOC_OBJECT o
  ON o.DOC_VERSION_ID = l.DOC_VERSION_ID
 AND o.OBJECT_ID = l.TARGET_OBJECT_ID
WHERE l.DOC_VERSION_ID = :versionId
  AND l.SOURCE_OBJECT_ID = :objectId;
```

Таким чином можна будувати пошук залежностей, аналізувати з'єднання, перевіряти цілісність схем і формувати інформаційні картки.

## 5. А як бути із ЗВТ та відгалуженнями?

У твоєму редакторі це навіть цікавіший випадок.

Наприклад, є основна лінія, до якої приєднано відгалуження, а на кінці відгалуження розташований ЗВТ.

У цьому випадку логічні зв'язки можуть виглядати так:

| SOURCE_OBJECT_ID | TARGET_OBJECT_ID | LINK_TYPE   |
| ---------------- | ---------------- | ----------- |
| BRANCH-001       | EDGE-001         | ATTACHED_TO |
| ZVT-001          | BRANCH-001       | MOUNTED_ON  |

Для цього `BRANCH-001` і `ZVT-001` також повинні бути представлені в `DOC_OBJECT`, якщо ти хочеш використовувати зовнішні ключі `DOC_OBJECT_LINK`.

Згодом можна буде отримати всі ЗВТ, підключені до конкретної лінії, без читання всього JSON.

Водночас точне місце приєднання відгалуження (сегмент, координата, параметр уздовж лінії) має залишатися в Snapshot. Якщо потрібен SQL-пошук за сегментом, його ідентифікатор можна додатково записати в `SEGMENT_ID`.

## 6. Чим DOC_OBJECT_LINK відрізняється від DOC_RELATION і DOC_CROSS_LINK?

Це три різні рівні зв'язків.

| Таблиця           | Що пов'язує                                         | Приклад                                              |
| ----------------- | --------------------------------------------------- | ---------------------------------------------------- |
| `DOC_OBJECT_LINK` | Об'єкти в межах однієї версії схеми                 | EDGE підключений до NODE                             |
| `DOC_RELATION`    | Документи між собою                                 | Схема обладнання належить до плану поверху           |
| `DOC_CROSS_LINK`  | Об'єкт однієї схеми з іншим документом або об'єктом | Натиснути на насос і перейти до його детальної схеми |

Тобто `DOC_OBJECT_LINK` — це внутрішня топологія схеми, а дві інші таблиці відповідають за міждокументні відношення та переходи.

## 7. Чи потрібно оновлювати DOC_OBJECT_LINK при кожному Save?

Так, якщо ти хочеш, щоб SQL-запити завжди повертали актуальні зв'язки.

Але це не означає створення нових записів історії.

Твій API отримує повний Snapshot і в межах однієї транзакції:

1. Оновлює `DOC_SNAPSHOT`.
2. Синхронізує `DOC_OBJECT`.
3. Синхронізує `DOC_OBJECT_ATTRIBUTE`.
4. Синхронізує `DOC_OBJECT_LINK`.
5. Виконує `COMMIT`.

Якщо зв'язок не змінився, його можна залишити без змін. Якщо з'явився новий — вставити. Якщо зв'язок видалено — прибрати відповідний запис.

Для `DOC_OBJECT_LINK` доцільно використовувати стабільний `LINK_ID` або визначений унікальний ключ логічного зв'язку, щоб не накопичувати дублікати.

## Моя рекомендація для твоєї системи

Залишити `DOC_OBJECT_LINK`, але використовувати її виключно для логічних зв'язків, а не для дублювання геометрії.

При цьому я пропоную поступово заповнювати її трьома категоріями: підключення EDGE до NODE, приєднання BRANCH до NODE/EDGE та приєднання ЗВТ до BRANCH.

На першому етапі можна повністю реалізувати `DOC_SNAPSHOT`, `DOC_OBJECT` і `DOC_OBJECT_ATTRIBUTE`, а `DOC_OBJECT_LINK` додати після уточнення моделі підключень.

Для наступного кроку мені потрібно побачити один реальний об'єкт `edge` із Zustand, особливо вміст `start.attached` і `end.attached`. Тоді я покажу, як із твоєї структури автоматично формувати `DOC_OBJECT_LINK`, не змінюючи вже реалізовану логіку Canvas.
