Next.js + Konva + Zustand + Node.js API + Oracle 21
JavaScript, без TypeScript

1. РІШЕННЯ
Впровадити RBAC (ролі та permissions) + ABAC (умови) + scope (область дії).
Не створювати окремі ролі на кожну комбінацію цеху, посади та типу схеми.
Кожне призначення ролі зберігає власні scope та schemeTypes. Не можна об'єднувати всі permissions окремо від усіх scope: це призведе до підвищення привілеїв.
За замовчуванням — deny. Порожній або неповний контекст ресурсу — deny.

2. МОДЕЛЬ
Subject: id, active, memberships, assignments.
Assignment: roleId, scope: {kind:'global'|'unit'|'workshop'|'department'|'album'|'scheme', id}, schemeTypes: ['equipment'], optional conditions.
Role: code + permissions.
Resource: id, type, schemeType, unitId, workshopId, departmentId, albumId, schemeId, ownerId, status.
Довірені атрибути користувача та ресурсу сервер отримує з БД, а не з клієнтського JSON.

Permissions: app.access, album.list, album.view, album.create, album.update, album.delete, scheme.list, scheme.view, scheme.create, scheme.update, scheme.delete, scheme.export, scheme.save, element.card.view, element.card.edit, drawing.node.create/update/delete, drawing.edge.create/update/delete, drawing.zvt.create/update/delete, drawing.branch.create/update/delete, drawing.annotation.create/update/delete, drawing.specification.update, drawing.object.move, attachment.view/add/delete, notes.view/edit, admin.users.view, admin.roles.assign/revoke.

reader: app.access, album.list/view, scheme.list/view, element.card.view, attachment.view, notes.view (за політикою), scheme.export (якщо дозволено).
editor: права reader + відповідні create/update/delete та save, але лише у власному scope.
administrator: управління користувачами та призначеннями в делегованому scope; НЕ обов'язково editor.
super_administrator: ширше адміністрування за окремими політиками, з аудитом.
Посада — атрибут або окремий policy grant; цех/unit — scope або атрибут, а не окрема роль.

3. ПРИКЛАД
Користувач має editor в unit U1 для equipment, reader в workshop W2 для premises.
Він редагує equipment U1, переглядає premises W2, але не редагує premises W2.
Всі умови повинні збігатися в межах ОДНОГО assignment/grant.

5. ПРИКЛАД ЧИСТОЇ POLICY-ФУНКЦІЇ (JS)
// src/features/auth/model/accessPolicy.js
export function can(subject, permission, resource, rolePermissions) {
  if (!subject?.active || !resource?.type || !Array.isArray(subject.assignments)) return false;
  return subject.assignments.some(a => {
    if (!(rolePermissions[a.roleId] || []).includes(permission)) return false;
    if (a.schemeTypes?.length && !a.schemeTypes.includes(resource.schemeType)) return false;
    const s = a.scope;
    if (!s) return false;
    switch (s.kind) {
      case 'global': return true;
      case 'unit': return !!resource.unitId && s.id === resource.unitId;
      case 'workshop': return !!resource.workshopId && s.id === resource.workshopId;
      case 'department': return !!resource.departmentId && s.id === resource.departmentId;
      case 'album': return !!resource.albumId && s.id === resource.albumId;
      case 'scheme': return !!resource.schemeId && s.id === resource.schemeId;
      default: return false;
    }
  });
}
// Це демонстраційне ядро: production має також перевіряти статус,
// спадкування, чинність призначень, explicit deny (якщо додасте),
// membership, класифікацію ресурсу та правила адміністративного делегування.

6. КОНТРОЛЕР І ZUSTAND
Не переписувати всі Konva nodes/edges/ZVT/branches/annotations.
Створити одну таблицю команд: addNode->drawing.node.create, moveNode->drawing.object.move, addZvt->drawing.zvt.create, addBranch->drawing.branch.create, deleteAttachment->attachment.delete, editCard->element.card.edit, saveScheme->scheme.save.
Всі наявні публічні mutating methods маршрутизувати через executeGuardedCommand(permission, resource, callback).
Контекст активної схеми брати з актуального state, не кешувати контекст попередньої схеми.
UI state (selection, pan, zoom, opened card) залишити доступним reader.
Document state (nodes, edges, zvt, zvtBranches, annotation, specificationTable, attachments, notes) змінювати лише через перевірені команди.
Врахувати keyboard shortcuts, drag-and-drop, context menu, undo/redo, import, copy/paste, bulk operations, autosave.
Прямий useCanvasStore.setState не є безпековою межею — API все одно перевіряє всі записи.

7. РЕЖИМ URL
?mode=editor може бути лише UX-побажанням.
const canEdit = useCan('scheme.update', currentScheme);
const actualMode = requestedMode === 'editor' && canEdit ? 'editor' : 'viewer';
Сервер при GET перевіряє scheme.view, при PUT/POST/PATCH — відповідний permission на конкретну схему.
Якщо користувач втратив доступ, інтерфейс переходить у viewer, незбережені операції блокуються, API повертає 403.

8. NODE.JS API — СПРАВЖНЯ МЕЖА БЕЗПЕКИ
На кожен запит: authenticate -> завантажити користувача та grants -> завантажити ресурс з Oracle -> authorize -> виконати дію.
Не довіряти ролям, unitId, schemeType або departmentId із браузера.
GET /api/schemes фільтрує записи за доступними ресурсами; GET /api/schemes/:id перевіряє scheme.view.
PUT /api/schemes/:id перевіряє scheme.save та scheme.update, незалежно від того, чи користувач надіслав цілий JSON чи окремі об'єкти.
Якщо потрібні різні права на типи змін, сервер порівнює попередній/новий документ і перевіряє кожну змінену категорію; альтернативно — API команд із конкретними діями.
Зберігати JSON і реляційні сутності в одній транзакції Oracle; перевірку доступу виконувати до запису, а для критичних операцій врахувати конкурентні зміни/версію документа.
GET вкладень і download URL також захищати. Захистити від IDOR, CSRF (для cookie sessions), витоку даних через кеш і export.

ВИСНОВОК
Оптимальний шлях для наявного коду: одна policy-функція + одна таблиця відповідності команд permissions + guards на контролері та Node.js API. Konva-компоненти та Zustand-модель схеми залишаються переважно без змін. Безпека забезпечується сервером, не URL і не frontend store.
