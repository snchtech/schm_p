Для твоєї системи Next.js + Konva + Node.js API + Oracle 21c я рекомендую зробити Oracle Database основним сховищем файлів вкладень, а файлову систему сервера використовувати лише для резервних копій.

При цьому важливо розділити три сутності:

1. `DOC_OBJECT` — графічний об'єкт вкладення на схемі, його ідентифікатор, тип, метадані та прив'язка.
2. `FILE_ASSET` — фізичний файл (PDF, PNG, JPEG, SVG тощо), його вміст, розмір, MIME-тип і контрольна сума.
3. `DOC_ASSET_REF` — зв'язок між графічним об'єктом і файлом.

У твоїй раніше розробленій структурі Oracle таблиці `FILE_ASSET` і `DOC_ASSET_REF` уже передбачені. Тобто не потрібно створювати всю архітектуру заново — достатньо доопрацювати ці таблиці для зберігання файлів безпосередньо в Oracle.

## 1. Як це працюватиме

Логічна модель збереження вкладення в Oracle

На твоєму скриншоті вкладення має власний `id`, `attachedTo`, `offsetX`, `offsetY`, а також об'єкт `file`, який містить назву, тип, розмір і шлях до файлу.

Цю структуру можна майже повністю зберегти. Потрібно лише замінити залежність від `storageKey` файлової системи на `ASSET_ID` у базі.

## 2. Що саме зберігати в кожній таблиці

| Таблиця           | Що зберігати                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------ |
| `DOC_OBJECT`      | `OBJECT_ID`, `OBJECT_TYPE='ATTACHMENT'`, `OBJECT_JSON` з `offsetX`, `offsetY`, `comment`, `attachedTo` |
| `DOC_OBJECT_LINK` | Зв'язок вкладення з `NODE` або `EDGE`, наприклад `ATTACHED_TO`                                         |
| `DOC_ASSET_REF`   | `DOC_VERSION_ID`, `OBJECT_ID`, `ASSET_ID`, `USAGE_TYPE='attachment'`                                   |
| `FILE_ASSET`      | `ID`, `ORIGINAL_NAME`, `MIME_TYPE`, `BYTE_SIZE`, `FILE_CONTENT` типу `BLOB`, `SHA256`                  |

Важливо: `DOC_OBJECT_LINK` описує, до якого елемента схеми прикріплено вкладення, а `DOC_ASSET_REF` — який саме фізичний файл належить цьому вкладенню. Це два різні зв'язки.

## 3. Як зберігати сам файл в Oracle

Для цього використовуй тип даних `BLOB` — він призначений для бінарного вмісту файлів.

У твоїй наявній таблиці `FILE_ASSET` можна додати:

```
ALTER TABLE FILE_ASSET
ADD FILE_CONTENT BLOB;
```

Тоді один запис `FILE_ASSET` міститиме, наприклад:

| Поле               | Значення           |
| ------------------ | ------------------ |
| `ID`               | UUID файла         |
| `ORIGINAL_NAME`    | Тестовий_pdf.pdf   |
| `MIME_TYPE`        | application/pdf    |
| `BYTE_SIZE`        | 172337             |
| `STORAGE_PROVIDER` | blob               |
| `SHA256`           | Контрольна сума    |
| `FILE_CONTENT`     | Бінарний вміст PDF |

У твоєму поточному DDL `STORAGE_KEY` обов'язковий, тому під час міграції його потрібно або заповнювати технічним значенням, або змінити обмеження `NOT NULL`.

Для PNG, JPEG, PDF, SVG та інших форматів використовуватиметься однакова структура. Не потрібно створювати окремі таблиці для кожного формату.

## 4. Як працюватиме завантаження та перегляд

Завантаження

Next.js надсилає файл у Node.js API. API перевіряє права, формат і розмір, після чого записує BLOB у `FILE_ASSET`, створює прив'язки та повертає `assetId`.

Перегляд

Модальне вікно вкладень звертається до API. API перевіряє доступ і повертає вміст файла з Oracle BLOB, а не з каталогу проєкту.

Резервна копія

Після успішного збереження окремий процес копіює файл з Oracle у резервний каталог сервера. При цьому застосунок ніколи не читає файл із цього каталогу.

Для резервних копій я рекомендую використовувати окремий каталог, наприклад `/srv/backup/attachments`, а не каталог вихідного коду Next.js або API. У Docker його можна підключити як окремий volume.

Важливо: резервна копія на тому самому сервері не замінює повноцінного резервного копіювання Oracle та зберігання копій на незалежному носії.

## 5. Як це виглядатиме у Zustand

Твій поточний формат можна спростити до:

```
{
  "id": "attachment-001",
  "kind": "attachment",
  "attachedTo": {
    "type": "node",
    "id": "node-001"
  },
  "assetId": "asset-001",
  "offsetX": 18.69,
  "offsetY": 16.31,
  "comment": "",
  "file": {
    "originalName": "Тестовий_pdf.pdf",
    "mimeType": "application/pdf",
    "size": 172337
  }
}
```

У Zustand та JSON-знімку схеми не потрібно зберігати сам файл у Base64. Достатньо `assetId` і метаданих.

Окремо врахуй версійність: коли створюється новий `DRAFT`, копіюються прив'язки до файлів, але сам BLOB повторно записувати не потрібно. Так старі `STABLE` та `ARCHIVED` версії збережуть свої вкладення.
