Саме тому для твоєї системи я рекомендую не створювати новий запис при кожному автозбереженні, а оновлювати один і той самий запис поточної DRAFT-версії.

У нашій архітектурі потрібно чітко розмежувати збереження документа та створення нової версії документа. Це різні операції.

## 1. Як має працювати автозбереження

Припустимо, користувач працює над схемою обладнання протягом п'яти годин, а автозбереження виконується кожні три хвилини.

DOC_VERSION

DRAFT v2

Одна версія

DOC_SNAPSHOT

| DOC_VERSION_ID | `draft-v2`               |
| -------------- | ------------------------ |
| SAVE_REVISION  | 100                      |
| SNAPSHOT_JSON  | Останній актуальний JSON |

100 автозбережень → 1 запис DOC_SNAPSHOT, 1 версія DRAFT, а не 100 нових документів.

Кожне автозбереження просто виконує `UPDATE` наявного рядка.

## 2. SQL для автозбереження

```
UPDATE DOC_SNAPSHOT
SET
    SNAPSHOT_JSON = :snapshotJson,
    SAVE_REVISION = SAVE_REVISION + 1,
    UPDATED_AT = SYSTIMESTAMP
WHERE DOC_VERSION_ID = :versionId
  AND SAVE_REVISION = :expectedRevision;
```

`UPDATED_AT` використовуй, якщо ця колонка є в твоїй фактичній структурі `DOC_SNAPSHOT`.

Для першого збереження, коли запису ще немає, виконується `INSERT`. Усі наступні збереження — `UPDATE`.

`SAVE_REVISION` — це лише лічильник успішних збережень, не окремі записи історії.

## 3. Що відбувається з індексованими NODE та EDGE?

Тут також не потрібно створювати нові версії об'єктів при кожному автозбереженні.

Для поточної DRAFT використовуємо:

- `MERGE` — оновлюємо наявні NODE/EDGE або вставляємо нові.
- `DELETE` — видаляємо об'єкти, яких більше немає у Snapshot, з урахуванням зовнішніх ключів.
- Синхронізацію атрибутів та зв'язків — лише в межах тієї самої `DOC_VERSION_ID`.

У результаті, якщо на Canvas є 500 NODE та 300 EDGE, після сотні автозбережень у `DOC_OBJECT` залишиться приблизно 800 актуальних записів цих типів, а не 80 000.

## 4. Я рекомендую ще одну оптимізацію

Не запускати автозбереження, якщо схема не змінювалася.

У Zustand можна мати:

```
isDirty: false,
isSaving: false,
```

Коли користувач змінює NODE, EDGE або інші документні дані, встановлюємо `isDirty = true`.

Автозбереження виконується тільки якщо є зміни. Під час запиту потрібно зафіксувати ревізію локальних змін, щоб редагування, зроблені вже після відправлення JSON, не були помилково позначені як збережені.

Також рекомендую не запускати друге збереження, поки перше ще виконується.

## 5. Коли створюється новий запис DOC_VERSION?

Тільки при переході між офіційними версіями документа:

| Операція                             | Нова DOC_VERSION?     | Новий DOC_SNAPSHOT?          |
| ------------------------------------ | --------------------- | ---------------------------- |
| Перемістити NODE                     | Ні                    | Ні                           |
| Натиснути Save                       | Ні                    | Ні, якщо вже існує           |
| Автозбереження                       | Ні                    | Ні, якщо вже існує           |
| Закрити та знову відкрити DRAFT      | Ні                    | Ні                           |
| Опублікувати DRAFT як STABLE         | Ні, змінюється статус | Ні                           |
| Створити нову DRAFT на основі STABLE | Так                   | Так, копія початкового стану |

Таким чином історія формується за офіційними версіями документа, а не за кількістю натискань Save.

## 6. Важлива деталь щодо Oracle

Навіть якщо ми оновлюємо один рядок CLOB, Oracle фізично виконує роботу з новими даними та використовує механізми UNDO/REDO. Тому 100 автозбережень — це не нульове навантаження.

Але це не означає, що в таблиці з'являться 100 Snapshot.

Для великих схем я рекомендую інтервал автозбереження 2–5 хвилин за наявності змін, а ручне збереження — в будь-який момент.

Отже, для твого проєкту найкраща модель — один актуальний Snapshot на кожну DOC_VERSION, який багаторазово оновлюється протягом роботи над DRAFT. Індексовані таблиці синхронізуються в тій самій транзакції. Це дозволяє підтримувати автозбереження без накопичення сотень непотрібних записів.
