АРХІТЕКТУРА ЗБЕРІГАННЯ СХЕМ У ORACLE 21c
Next.js + Konva + Node.js API | Проєкт «Альбом схем»
Дата: 23.09.2026

1. РІШЕННЯ

Рекомендована гібридна модель:
• SCHEME — сутність схеми, прив'язана до наявного альбому.
• SCHEME_REVISION — версія повного JSON-документа Konva/редактора, щоб швидко відкривати схему та відновлювати її стан.
• SCHEME_ELEMENT — індексовані структурні дані кожного об'єкта, конектора (edge), branch, ЗВТ та вкладеної схеми/приміщення.
• ELEMENT_PARAMETER — додаткові типізовані параметри екземпляра елемента.
• ELEMENT_LINK — семантичні зв'язки (наприклад, «цей елемент посилається на іншу схему»), відокремлені від графічних edge.
• EXTERNAL_OBJECT_REF — зв'язок елемента з об'єктом загальної БД; підтримує кілька зовнішніх систем/ідентифікаторів.

Не зберігати виключно JSON: для пошуку за зовнішнім ID, належністю до схеми, типом приміщення, параметрами й аналізу зв'язків потрібні окремі індексовані таблиці. Водночас не намагатися відтворювати весь Konva JSON у колонках: геометрія, стиль, контрольні точки та специфічні властивості залишаються в JSON.

2. РОЗМЕЖУВАННЯ ПОНЯТЬ

scheme_type: equipment | floor_plan | process | ... — тип документа/схеми.
element_kind: node | edge | branch | instrument | room | scheme_ref | group | annotation — технічний тип екземпляра.
element_type_code: pump | valve | wall | door | office_room | ... — конкретний графічний/предметний тип із бібліотеки.
target_entity_type: scheme | room | equipment | external_object — семантичний об'єкт, на який посилається елемент.

Одна схема може містити room, equipment та scheme_ref, якщо її конфігурація це дозволяє. Приміщення може бути як графічним елементом плану, так і окремою предметною сутністю ROOM. Не ототожнювати ROOM з Konva node: одне приміщення може з'являтися на різних схемах або версіях.

3. ЗВ'ЯЗОК ІЗ НАЯВНИМИ ТАБЛИЦЯМИ

Залишити чинні таблиці альбомів і схем. Нижче SCHEME — логічна назва вашої наявної таблиці: адаптувати імена колонок і типи ключів, не створювати її вдруге. Додати scheme_type_code, current_revision_id (після створення SCHEME_REVISION) і, за потреби, template_id. Для альбому залишити існуючий FK. Міграції виконувати поетапно з перевіркою наявних PK/FK.

4. БАЗОВА DDL ДЛЯ ORACLE 21c (ПРИКЛАД)

-- У прикладі SCHEME.ID і APP_USER.ID — NUMBER; адаптуйте до чинної схеми.
-- Для великих JSON використовуйте CLOB CHECK (json_data IS JSON).

CREATE TABLE SCHEME_TYPE (
  CODE VARCHAR2(60) PRIMARY KEY,
  NAME VARCHAR2(200) NOT NULL,
  IS_ACTIVE NUMBER(1) DEFAULT 1 NOT NULL CHECK (IS_ACTIVE IN (0,1))
);

CREATE TABLE SCHEME_TEMPLATE (
  ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  SCHEME_TYPE_CODE VARCHAR2(60) NOT NULL REFERENCES SCHEME_TYPE(CODE),
  NAME VARCHAR2(200) NOT NULL,
  TEMPLATE_VERSION NUMBER DEFAULT 1 NOT NULL,
  CONFIG_JSON CLOB CHECK (CONFIG_JSON IS JSON),
  IS_ACTIVE NUMBER(1) DEFAULT 1 NOT NULL CHECK (IS_ACTIVE IN (0,1))
);

-- У чинній SCHEME додати лише відсутні поля:
-- ALTER TABLE SCHEME ADD (SCHEME_TYPE_CODE VARCHAR2(60), TEMPLATE_ID NUMBER);
-- Після міграції даних встановити NOT NULL та FK для SCHEME_TYPE_CODE.

CREATE TABLE SCHEME_REVISION (
  ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  SCHEME_ID NUMBER NOT NULL REFERENCES SCHEME(ID),
  REVISION_NO NUMBER NOT NULL,
  JSON_SCHEMA_VERSION NUMBER DEFAULT 1 NOT NULL,
  DOCUMENT_JSON CLOB NOT NULL CHECK (DOCUMENT_JSON IS JSON),
  CREATED_BY NUMBER NOT NULL, -- FK на таблицю користувачів після звірки з чинною моделлю
  CREATED_AT TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
  CHANGE_NOTE VARCHAR2(1000),
  CONSTRAINT UQ_SCHEME_REV UNIQUE (SCHEME_ID, REVISION_NO),
  CONSTRAINT UQ_SCHEME_REV_PAIR UNIQUE (SCHEME_ID, ID)
);

-- Після створення SCHEME_REVISION можна додати до SCHEME CURRENT_REVISION_ID.
-- Контроль належності revision до scheme забезпечити складеним FK або транзакційною перевіркою.

CREATE TABLE ELEMENT_TYPE (
  CODE VARCHAR2(100) PRIMARY KEY,
  ELEMENT_KIND VARCHAR2(40) NOT NULL,
  NAME VARCHAR2(200) NOT NULL,
  DEFAULT_PROPS_JSON CLOB CHECK (DEFAULT_PROPS_JSON IS JSON),
  PARAM_SCHEMA_JSON CLOB CHECK (PARAM_SCHEMA_JSON IS JSON)
);

CREATE TABLE SCHEME_ELEMENT (
  ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  SCHEME_ID NUMBER NOT NULL REFERENCES SCHEME(ID),
  CLIENT_ID VARCHAR2(100) NOT NULL,
  ELEMENT_KIND VARCHAR2(40) NOT NULL,
  ELEMENT_TYPE_CODE VARCHAR2(100) REFERENCES ELEMENT_TYPE(CODE),
  NAME VARCHAR2(500),
  SOURCE_CLIENT_ID VARCHAR2(100), -- edge/branch: початковий елемент
  TARGET_CLIENT_ID VARCHAR2(100), -- edge: кінцевий елемент
  ATTACHED_TO_CLIENT_ID VARCHAR2(100), -- branch: node або edge
  BRANCH_CLIENT_ID VARCHAR2(100), -- ЗВТ: branch, до якого належить
  ROOM_ID NUMBER,
  PROPS_JSON CLOB CHECK (PROPS_JSON IS JSON),
  CREATED_AT TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
  UPDATED_AT TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
  CONSTRAINT UQ_SCHEME_ELEMENT_CLIENT UNIQUE (SCHEME_ID, CLIENT_ID),
  CONSTRAINT UQ_SCHEME_ELEMENT_SCHEME_ID UNIQUE (SCHEME_ID, ID)
);
CREATE INDEX IX_SCHEME_ELEMENT_KIND ON SCHEME_ELEMENT (SCHEME_ID, ELEMENT_KIND);
CREATE INDEX IX_SCHEME_ELEMENT_TYPE ON SCHEME_ELEMENT (ELEMENT_TYPE_CODE);
CREATE INDEX IX_SCHEME_ELEMENT_ROOM ON SCHEME_ELEMENT (ROOM_ID);

-- Опціонально: забезпечити, що source/target/attachedTo/branch існують
-- У межах тієї ж схеми складеними FK (SCHEME_ID, ..._CLIENT_ID)
-- до SCHEME_ELEMENT(SCHEME_ID, CLIENT_ID). Зважати на порядок вставки
-- та циклічні посилання; можна встановити DEFERRABLE INITIALLY DEFERRED.

CREATE TABLE ROOM (
  ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  ROOM_TYPE_CODE VARCHAR2(60) NOT NULL,
  EXTERNAL_ROOM_ID VARCHAR2(200),
  BUILDING_CODE VARCHAR2(100),
  FLOOR_NO NUMBER,
  ROOM_NO VARCHAR2(50),
  NAME VARCHAR2(300),
  ATTRIBUTES_JSON CLOB CHECK (ATTRIBUTES_JSON IS JSON)
);
ALTER TABLE SCHEME_ELEMENT ADD CONSTRAINT FK_ELEMENT_ROOM
  FOREIGN KEY (ROOM_ID) REFERENCES ROOM(ID);

CREATE TABLE ELEMENT_PARAMETER (
  ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  ELEMENT_ID NUMBER NOT NULL REFERENCES SCHEME_ELEMENT(ID) ON DELETE CASCADE,
  PARAM_CODE VARCHAR2(100) NOT NULL,
  VALUE_TYPE VARCHAR2(20) NOT NULL CHECK (VALUE_TYPE IN ('string','number','boolean','date','json')),
  VALUE_STRING VARCHAR2(4000),
  VALUE_NUMBER NUMBER,
  VALUE_DATE DATE,
  VALUE_JSON CLOB CHECK (VALUE_JSON IS JSON),
  CONSTRAINT UQ_ELEMENT_PARAM UNIQUE (ELEMENT_ID, PARAM_CODE)
);
CREATE INDEX IX_ELEMENT_PARAM_SEARCH ON ELEMENT_PARAMETER (PARAM_CODE, VALUE_STRING);
CREATE INDEX IX_ELEMENT_PARAM_NUMBER ON ELEMENT_PARAMETER (PARAM_CODE, VALUE_NUMBER);

CREATE TABLE EXTERNAL_OBJECT_REF (
  ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  ELEMENT_ID NUMBER NOT NULL REFERENCES SCHEME_ELEMENT(ID) ON DELETE CASCADE,
  SOURCE_SYSTEM VARCHAR2(100) NOT NULL,
  EXTERNAL_ENTITY_TYPE VARCHAR2(100) NOT NULL,
  EXTERNAL_ID VARCHAR2(200) NOT NULL,
  IS_PRIMARY NUMBER(1) DEFAULT 0 NOT NULL CHECK (IS_PRIMARY IN (0,1)),
  CONSTRAINT UQ_ELEMENT_EXTERNAL UNIQUE (ELEMENT_ID, SOURCE_SYSTEM, EXTERNAL_ENTITY_TYPE, EXTERNAL_ID)
);
CREATE INDEX IX_EXTERNAL_REF_LOOKUP ON EXTERNAL_OBJECT_REF
  (SOURCE_SYSTEM, EXTERNAL_ENTITY_TYPE, EXTERNAL_ID);

CREATE TABLE ELEMENT_LINK (
  ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  SOURCE_ELEMENT_ID NUMBER NOT NULL REFERENCES SCHEME_ELEMENT(ID) ON DELETE CASCADE,
  LINK_TYPE VARCHAR2(60) NOT NULL,
  TARGET_SCHEME_ID NUMBER REFERENCES SCHEME(ID),
  TARGET_ROOM_ID NUMBER REFERENCES ROOM(ID),
  TARGET_ELEMENT_ID NUMBER REFERENCES SCHEME_ELEMENT(ID),
  CONSTRAINT CK_ELEMENT_LINK_TARGET CHECK (
    (CASE WHEN TARGET_SCHEME_ID IS NOT NULL THEN 1 ELSE 0 END) +
    (CASE WHEN TARGET_ROOM_ID IS NOT NULL THEN 1 ELSE 0 END) +
    (CASE WHEN TARGET_ELEMENT_ID IS NOT NULL THEN 1 ELSE 0 END) = 1
  )
);
CREATE INDEX IX_LINK_TARGET_SCHEME ON ELEMENT_LINK (TARGET_SCHEME_ID);
CREATE INDEX IX_LINK_TARGET_ROOM ON ELEMENT_LINK (TARGET_ROOM_ID);

5. ДОДАТКОВІ ДОВІДНИКИ Й ШАБЛОНИ

ROOM_TYPE: office, corridor, technical, warehouse тощо.
ROOM_TEMPLATE: room_type_code, template_version, fields_json (опис полів, типів, обов'язковості, одиниць вимірювання).
SCHEME_TYPE_ELEMENT_TYPE: scheme_type_code + element_type_code + allowed_operations_json — які типи елементів дозволені в кожному типі схеми.
DEPARTMENT_ELEMENT_LIBRARY: department_id + element_type_code — дозволений набір підрозділу.
USER_ELEMENT_PREFERENCE: user_id + scheme_type_code + element_type_code + is_visible — особистий вибір з доступного набору.

Глобальний тип елемента не дублюється для кожного підрозділу: підрозділ отримує посилання на запис ELEMENT_TYPE або на версію шаблону. Користувач бачить перетин: дозволено для типу схеми ∩ доступно підрозділу/загальній бібліотеці ∩ персонально не приховано. Видача бібліотеки редактора лише за перевіреної комбінації editor + роль потрібного підрозділу + право редагування типу схеми. Reader бачить збережені елементи схеми, але не палітру додавання. Перевіряти права також на API, а не тільки в UI.

6. ПРИКЛАД JSON-ДОКУМЕНТА СХЕМИ

{
  "schemaVersion": 1,
  "schemeId": 125,
  "schemeType": "equipment",
  "templateId": 4,
  "viewport": { "x": 0, "y": 0, "scale": 1 },
  "elements": [
    {
      "id": "node-1", "kind": "node", "type": "pump", "name": "Насос Н-1",
      "geometry": { "x": 100, "y": 150, "rotation": 0 },
      "props": { "diameter": 100 },
      "externalRefs": [{ "sourceSystem": "EQUIPMENT_DB", "entityType": "equipment", "id": "EQ-2045" }]
    },
    { "id": "node-2", "kind": "scheme_ref", "type": "linked_scheme", "name": "Схема № 126",
      "geometry": { "x": 350, "y": 150 }, "link": { "targetType": "scheme", "targetId": 126 } },
    { "id": "edge-1", "kind": "edge", "type": "pipe", "sourceId": "node-1", "targetId": "node-2",
      "points": [100,150,200,150,200,180,350,180] }
  ]
}

Зберігати власний незалежний JSON редактора (а не покладатися виключно на stage.toJSON()): це дозволяє мігрувати модель, валідувати зв'язки та змінювати реалізацію Konva. JSON документа є знімком, а SCHEME_ELEMENT та дочірні таблиці — поточним індексованим станом. Усі вони оновлюються однією транзакцією.

7. API ТА АТОМАРНЕ ЗБЕРЕЖЕННЯ

GET /api/schemes/:id — метадані та поточна ревізія JSON.
PUT /api/schemes/:id/document — повний валідований документ + expectedRevision.
GET /api/schemes/:id/elements — індексований перелік об'єктів.
GET /api/elements/search?sourceSystem=...&externalId=... — пошук за загальним ID.
GET /api/rooms/:id/schemes — схеми, де присутнє приміщення.
GET /api/schemes/:id/revisions — історія.
POST /api/schemes/:id/restore/:revision — створення НОВОЇ ревізії з історичної.

Алгоритм PUT:
1) Автентифікація; перевірка editor + підрозділ + право на тип схеми + доступ до конкретної схеми.
2) Перевірка schemaVersion, структури, унікальності clientId, допустимих elementType, коректності source/target/branch та target scheme/room.
3) BEGIN TRANSACTION; SELECT ... FROM SCHEME WHERE ID=:id FOR UPDATE.
4) Порівняти expectedRevision із поточною ревізією; якщо різні — HTTP 409 без перезапису чужих змін.
5) INSERT SCHEME_REVISION з новим JSON; синхронізувати SCHEME_ELEMENT, ELEMENT_PARAMETER, EXTERNAL_OBJECT_REF, ELEMENT_LINK за стабільним clientId. Для першої версії можна повністю замінювати дочірні записи; надалі краще UPSERT/MERGE, щоб зберігати постійні ELEMENT_ID для зовнішніх посилань.
6) Оновити SCHEME.CURRENT_REVISION_ID і UPDATED_AT; COMMIT. На будь-якій помилці ROLLBACK.

У Node.js використати одну Oracle connection і явну транзакцію; autoCommit=false до останнього кроку. Не приймати від клієнта довільні SCHEME_ID/ELEMENT_ID або власника без серверної перевірки. На GET фільтрувати схеми й пов'язані сутності за правами.

8. ПОШУК

За зовнішнім ID:
SELECT e.SCHEME_ID, e.ID, e.CLIENT_ID, e.NAME
FROM EXTERNAL_OBJECT_REF x
JOIN SCHEME_ELEMENT e ON e.ID = x.ELEMENT_ID
WHERE x.SOURCE_SYSTEM = :source_system
  AND x.EXTERNAL_ENTITY_TYPE = :entity_type
  AND x.EXTERNAL_ID = :external_id;

За прив'язкою до схеми:
SELECT * FROM SCHEME_ELEMENT WHERE SCHEME_ID = :scheme_id;

Усі схеми, що містять певне приміщення:
SELECT DISTINCT SCHEME_ID FROM SCHEME_ELEMENT WHERE ROOM_ID = :room_id;

Схеми, на які посилається поточна схема:
SELECT DISTINCT l.TARGET_SCHEME_ID
FROM ELEMENT_LINK l JOIN SCHEME_ELEMENT e ON e.ID = l.SOURCE_ELEMENT_ID
WHERE e.SCHEME_ID = :scheme_id AND l.TARGET_SCHEME_ID IS NOT NULL;

Для великих обсягів додати індекси за реальними запитами та, за потреби, JSON search index. Не індексувати всі поля JSON наперед.

9. ВАЖЛИВІ ПРАВИЛА ЦІЛІСНОСТІ

• Стабільний CLIENT_ID (UUID) генерується один раз при створенні елемента і не змінюється під час перетягування.
• Edge має валідні sourceId і targetId або явно описані вільні кінці, якщо це дозволяє редактор.
• Branch зберігає attachedTo {kind: node|edge, id}; ЗВТ — branchId. Видалення branch каскадно видаляє ЗВТ в JSON і структурному стані; видалення останнього ЗВТ видаляє branch.
• Посилання на іншу схему не означає фізичного вкладення JSON цієї схеми. Зберігати targetSchemeId, відкривати її окремо, контролювати цикли лише якщо бізнес-правила забороняють циклічні посилання.
• Видалення схеми/приміщення із зовнішніми посиланнями: за замовчуванням RESTRICT або soft delete; не каскадно знищувати інші схеми.
• Параметри з бібліотеки — визначення; ELEMENT_PARAMETER — значення конкретного екземпляра. Версіонувати шаблони, щоб старі схеми відкривалися після зміни бібліотеки.
• В історичних ревізіях є JSON, але SCHEME_ELEMENT описує лише ПОТОЧНУ ревізію. Для історичного пошуку знадобиться окрема індексація по ревізіях.
• Налаштувати аудит created_by/updated_by, резервне копіювання, обмеження розміру документа й перевірку зовнішніх ID через довірений API.

10. ПЛАН ВПРОВАДЖЕННЯ

Етап 1: перевірити чинні DDL альбомів/схем; додати тип схеми, ревізії та повний JSON; реалізувати GET/PUT із блокуванням версій.
Етап 2: ELEMENT_TYPE + SCHEME_ELEMENT, індексований пошук за схемою, node/edge/branch/ЗВТ.
Етап 3: EXTERNAL_OBJECT_REF, ELEMENT_PARAMETER і ELEMENT_LINK; пошук за загальним ID та перехід між схемами.
Етап 4: ROOM, ROOM_TYPE, ROOM_TEMPLATE і тип floor_plan; відображення одного ROOM на кількох схемах.
Етап 5: бібліотеки підрозділів, персональна видимість палітри, серверна перевірка комбінованих ролей.
Етап 6: аудит, міграції JSON schemaVersion, відновлення ревізій, оптимізація індексів.

Перед створенням production DDL необхідно звірити типи чинних PK/FK, таблицю користувачів і підрозділів, політику видалення, перелік elementKind та джерела зовнішніх ідентифікаторів. Приклади вище — стартова модель, а не міграція, яку слід виконувати без адаптації.
