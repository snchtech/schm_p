Так. Для твоєї системи attachments краще зберігати окремо від JSON Snapshot, і в нашій архітектурі Oracle 21c ми вже передбачали для цього таблиці `FILE_ASSET` та `DOC_ASSET_REF`.

Я рекомендую таку модель:

- `FILE_ASSET` — реєстр файлів: назва, MIME-тип, розмір, SHA-256, місце фізичного зберігання.
- `DOC_ASSET_REF` — зв'язок файлу з об'єктом конкретної версії схеми.
- `DOC_SNAPSHOT` — JSON із координатами, розмірами, налаштуваннями та `assetId`, але без самого вмісту файлу.

## 1. Де фізично зберігати файли?

Є два основні варіанти.

| Варіант              | Як працює                                      | Моя оцінка                                                  |
| -------------------- | ---------------------------------------------- | ----------------------------------------------------------- |
| Oracle BLOB          | Вміст PDF, SVG, PNG тощо зберігається в Oracle | Добре для централізованого резервування та контролю доступу |
| Файлове сховище / S3 | Oracle зберігає лише метадані та `STORAGE_KEY` | Краще для великої кількості або великих файлів              |

Для твого проєкту, якщо передбачається багато графічних файлів, PDF-підкладок і SVG-символів, я б обрав файлове сховище або S3-сумісне сховище з метаданими в Oracle. Якщо принципово потрібно тримати все всередині Oracle, можна додати окрему таблицю з BLOB.

## 3. Якщо зберігати файли безпосередньо в Oracle

Можна додати таблицю:

```
CREATE TABLE FILE_ASSET_CONTENT (
    ASSET_ID VARCHAR2(36) PRIMARY KEY,
    FILE_DATA BLOB NOT NULL,

    CONSTRAINT FK_ASSET_CONTENT
        FOREIGN KEY (ASSET_ID)
        REFERENCES FILE_ASSET(ID)
);
```

Тоді `FILE_ASSET` зберігатиме метадані, а `FILE_ASSET_CONTENT` — байти файлу. Це дозволить не змінювати модель зв'язків з об'єктами схеми.

## 4. Що важливо для версій STABLE і DRAFT

Припустимо, ти створив схему з PDF-підкладкою.

Коли STABLE копіюється в нову DRAFT, не потрібно фізично дублювати PDF. Обидві версії можуть посилатися на той самий `ASSET_ID`.

Якщо у DRAFT користувач змінить координати чи масштаб підкладки, зміниться тільки JSON. Якщо завантажить новий PDF, створюється новий `FILE_ASSET`, а старий залишається доступним для попередньої STABLE/ARCHIVED.

При цьому файл не можна видаляти зі сховища, доки на нього посилається хоча б одна версія документа.

## 5. Один нюанс у нашій поточній SQL-моделі

Раніше `DOC_ASSET_REF` ми прив'язували до `DOC_OBJECT` через `(DOC_VERSION_ID, OBJECT_ID)`.

Це добре для зображень, які є об'єктами на схемі. Але PDF-підкладка може належати всьому документу, а не конкретному NODE.

Тому я пропоную передбачити два типи прив'язок:

- файл до документа/версії — підкладка, загальні вкладення;
- файл до конкретного об'єкта — зображення, креслення, додаткова документація.

Можна реалізувати це окремими таблицями `DOC_VERSION_ASSET` і `DOC_OBJECT_ASSET`, щоб зовнішні ключі були чіткими.

Моя рекомендація: на першому етапі реалізувати `FILE_ASSET` + фізичне сховище файлів + `assetId` у Zustand. Після цього JSON Snapshot зможе повністю відтворювати схему, не роздуваючись через PDF, SVG і зображення.

І ще важливе питання для вибору структури: ти хочеш фізично зберігати PDF, SVG, PNG та інші файли саме в Oracle як BLOB чи на Linux-сервері, а в Oracle лише посилання на них?
