Так, ти правильно розумієш. Твій підхід — це пакетне збереження повного стану документа (Full Snapshot Save), а не відстеження та збереження кожної мікрозміни.

Але є одне важливе уточнення: тобі не потрібно очищати JSON у базі перед кожним збереженням. Ти просто замінюєш попередній JSON новим, актуальним знімком Zustand Store.

## 2. Що відбувається з JSON

Припустимо, у таблиці `DOC_SNAPSHOT` є запис:

```
DOC_VERSION_ID = 'version-001'
SAVE_REVISION = 5
SNAPSHOT_JSON = '{"nodes":[...],"edges":[...]}'
```

Після натискання «Зберегти» ти виконуєш оновлення:

```
UPDATE DOC_SNAPSHOT
SET SNAPSHOT_JSON = :newJson,
    SAVE_REVISION = SAVE_REVISION + 1
WHERE DOC_VERSION_ID = :versionId
  AND SAVE_REVISION = :expectedRevision
```

Якщо оновлено один рядок, збереження успішне. Якщо жодного — потрібно перевірити, чи це перше збереження, чи конфлікт версій.

Старий JSON замінюється новим. Не потрібно попередньо виконувати `DELETE` або очищати CLOB.

## 3. А що з індексованими таблицями?

Тут є два підходи.

|                       | Повна заміна                                       | Вибіркова синхронізація             |
| --------------------- | -------------------------------------------------- | ----------------------------------- |
| Принцип               | Видалити старі індексовані записи та вставити нові | Порівняти поточні й нові записи     |
| Складність            | Низька                                             | Вища                                |
| Навантаження          | Більше записів                                     | Менше записів                       |
| Зв'язки між об'єктами | Потрібно врахувати FK                              | Простіше зберігати незмінні зв'язки |
| Підходить для старту  | Так                                                | Для великих схем                    |

Для першого етапу я б використовував повну заміну індексованих даних поточної DRAFT з правильним порядком видалення залежних записів.

Однак якщо на NODE або EDGE посилаються інші таблиці, видалення може порушити зовнішні ключі. У такому разі краще використовувати `MERGE` для наявних об'єктів, `INSERT` для нових і `DELETE` для відсутніх.

## 4. Чи потрібна історія кожної зміни?

Ні. У твоєму випадку достатньо розділити три поняття:

- Мікрозміни — відбуваються лише у Zustand під час редагування.
- SAVE_REVISION — збільшується після кожного успішного збереження DRAFT. Використовується для контролю одночасного редагування, а не для зберігання історії.
- DOC_VERSION — офіційна версія документа (DRAFT, STABLE, ARCHIVED), яка має власний JSON та індексовані дані.

Наприклад:

Документ: Схема обладнання №15

Версії документа

STABLE v1

Незмінний JSON та індексовані об'єкти

DRAFT v2

SAVE_REVISION = 8

8 успішних збережень поточного чернеткового стану

STABLE v2

Після публікації DRAFT; попередня STABLE стає ARCHIVED

При цьому в нашій моделі публікація не вимагає повторного копіювання всіх NODE та EDGE: DRAFT уже має повний JSON і власні індексовані записи.

## 5. Чи підходить цей підхід для великих схем?

Так, але з одним застереженням.

Якщо схема містить 10 000 NODE та 15 000 EDGE, при кожному натисканні «Зберегти» ти передаєш увесь JSON. Це нормально для пакетного збереження, але повне видалення та повторна вставка 25 000 об'єктів у реляційні таблиці може створювати зайве навантаження.

Тому в майбутньому можна оптимізувати лише серверну синхронізацію індексованих таблиць, не змінюючи принципу роботи frontend.

Тобто Next.js і далі надсилатиме один повний Snapshot, а API сам визначатиме, які NODE або EDGE потрібно оновити.

Підсумок: твоя архітектура правильна для поставленого завдання: один централізований Zustand Store, одна кнопка Save, один API-запит, одна транзакція Oracle, повний JSON Snapshot та актуальні індексовані таблиці. Підтримка кожної мікрозміни в БД не потрібна.
