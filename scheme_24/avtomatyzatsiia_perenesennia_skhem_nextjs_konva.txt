АВТОМАТИЗАЦІЯ ПЕРЕНЕСЕННЯ ПАПЕРОВИХ СХЕМ У NEXT.JS + KONVA
Рекомендації, архітектура, JSON і поетапний план впровадження
Дата: 23.09.2026

1. КОРОТКА РЕКОМЕНДАЦІЯ

Найпрактичніший підхід — гібридний конвеєр: якісне сканування → вирівнювання та очищення → підкладка в Konva → напівавтоматичне розпізнавання символів і ліній → формування проміжного JSON → перевірка користувачем → конвертація у ВАШ поточний формат node/edge/branch/ЗВТ → збереження через API.

Не варто відразу доручати одній мультимодальній моделі генерувати готовий production-JSON для складної схеми. Модель може переплутати перетини з підключеннями, пропустити дрібні позначення або вигадати невидимі зв'язки. Розділіть розпізнавання геометрії, тексту, символів, топології та людську верифікацію.

2. ТРИ РЕЖИМИ РОБОТИ

А. ШВИДКИЙ СТАРТ: СКАН ЯК ПІДКЛАДКА
- Сканувати аркуші бажано 300–600 dpi, без перспективних спотворень; великі аркуші сканувати частинами з перекриттям або використовувати планшетний/широкоформатний сканер.
- Зберігати оригінал і окрему очищену копію PNG/WebP; PDF за потреби перетворювати на зображення для відображення.
- У Konva додати окремий заблокований Layer із Konva.Image: opacity, show/hide, brightness/contrast (попередня обробка файлу), масштабування, обертання та прив'язка двох контрольних точок.
- Поверх підкладки малювати наявними компонентами node/edge/branch/ЗВТ. Додати режими «підкладка», «трасування», «перевірка» та гарячі клавіші.
- Координати об'єктів зберігати в координатах схеми, а не екрана; матрицю трансформації підкладки зберігати окремо.
Це дає відчутне прискорення без тренування моделей.

Б. НАПІВАВТОМАТИЧНИЙ РЕЖИМ: OCR + КОМП'ЮТЕРНИЙ ЗІР
- OpenCV: вирівнювання, видалення шуму, адаптивна бінаризація, детекція прямих (HoughLinesP), пошук кіл і контурів, з'єднання сегментів.
- OCR: Tesseract або PaddleOCR для номерів, назв, підписів, діаметрів і умовних позначень. OCR не визначає топологію.
- Детектор символів: спочатку шаблонний пошук для стабільних символів, далі навчений детектор (наприклад, YOLO) на власних класах умовних позначень.
- Визначати точки стику, Т-подібні вузли, перетини без з'єднання, кінці ліній та орієнтацію елементів; неоднозначні місця позначати для ручної перевірки.
- Відображати пропозиції напівпрозорими Konva-об'єктами, з діями «прийняти», «виправити», «відхилити».

В. AI-АСИСТЕНТ: МУЛЬТИМОДАЛЬНА МОДЕЛЬ + ВАЛІДАТОР
- Надсилати не цілий великий аркуш одним зображенням, а оглядову копію та фрагменти високої роздільності з перекриттям.
- Додавати до запиту каталог ДОЗВОЛЕНИХ типів об'єктів, приклади символів, правила побудови та JSON Schema. Не дозволяти моделі створювати невідомі типи.
- Просити модель повернути лише ПРОМІЖНІ спостереження: знайдені символи, тексти, сегменти, ймовірні зв'язки, координати, confidence, sourceRegion і unresolvedIssues.
- Валідатор (Ajv/Zod) перевіряє структуру; геометричний і топологічний валідатори перевіряють зв'язки. Конвертер переводить перевірені дані в чинний формат редактора.
- Для технічно критичних схем AI ніколи не повинен непомітно затверджувати сумнівні підключення чи параметри.

3. РЕКОМЕНДОВАНА АРХІТЕКТУРА

Next.js (JavaScript, MUI, react-konva)
  ├── сторінка «Імпорт альбому»: завантаження PDF/JPEG/PNG, сторінки, метадані
  ├── Konva Stage: окремі шари background / suggestions / approved / selection
  ├── панель невизначеностей і редактор властивостей
  └── API-клієнт: старт задачі, статус, отримання JSON, підтвердження
          ↓
Node.js API
  ├── зберігання оригіналів і підкладок (локально/S3-compatible)
  ├── черга фонових задач (наприклад, BullMQ + Redis)
  ├── виклик Python CV worker через чергу або HTTP
  ├── адаптер мультимодальної моделі (необов'язково)
  ├── валідація JSON і мапінг до чинних компонентів
  └── БД: альбоми, аркуші, версії, об'єкти, джерела та історія підтверджень
          ↓
Python worker (окремий Docker-сервіс)
  ├── OpenCV / OCR / детектор власних символів
  ├── обробка фрагментів великих аркушів
  └── нормалізовані геометричні результати

Python потрібен не для редактора, а як зручний окремий сервіс комп'ютерного зору. Node.js залишається основним API. Почати можна взагалі без Python — лише з підкладки та ручного трасування.

4. ЯК ПІДГОТУВАТИ ВЛАСНИЙ КАТАЛОГ СИМВОЛІВ

- Експортувати ваші наявні компоненти у PNG/SVG-еталони, вказати тип, допустимі повороти, масштаб, порти підключення, текстові поля та правила прив'язки.
- Зібрати 20–50 репрезентативних аркушів різної якості для пілоту; для кожного розмітити символи, лінії, тексти, перетини і правильні з'єднання.
- Спочатку перевірити шаблонне розпізнавання та OCR. Якщо типів/варіацій багато — розмітити датасет для детектора символів.
- Розділити аркуші на train/validation/test за альбомами, щоб однакові або майже однакові аркуші не потрапили одночасно в навчання і тест.
- Окремо вимірювати recall символів, точність OCR, помилки зв'язності графа і час ручного виправлення. Головна метрика — скорочення часу перенесення ПІСЛЯ виправлень.

5. ПРОМІЖНИЙ JSON ДЛЯ РОЗПІЗНАВАННЯ (ПРИКЛАД, НЕ ФОРМАТ ВАШОЇ БД)

{
  "schemaVersion": "recognition.v1",
  "sheetId": "sheet-001",
  "source": { "fileId": "scan-001", "page": 1, "width": 4960, "height": 3508 },
  "coordinateSystem": "source-pixels",
  "symbols": [
    {
      "tempId": "s1", "class": "equipment-node", "bbox": [410, 250, 95, 95],
      "rotation": 0, "confidence": 0.94, "textRefs": ["t1"],
      "sourceRegion": [370, 210, 175, 175], "status": "proposed"
    }
  ],
  "texts": [
    { "tempId": "t1", "value": "К1", "bbox": [435, 350, 45, 20],
      "confidence": 0.89, "status": "proposed" }
  ],
  "segments": [
    { "tempId": "l1", "points": [[505, 298], [820, 298]],
      "confidence": 0.92, "status": "proposed" }
  ],
  "connections": [
    { "from": "s1", "to": "l1", "kind": "attached",
      "confidence": 0.81, "status": "needs-review" }
  ],
  "unresolvedIssues": [
    { "kind": "crossing-or-junction", "at": [820, 298],
      "candidates": ["connected", "crossing-only"], "status": "needs-review" }
  ]
}

У production-схемі зафіксувати допустимі enum-значення, типи, діапазони координат і мінімальну confidence. Confidence — оцінка моделі, а не гарантія правильності.

6. МАПІНГ У ВАШУ МОДЕЛЬ NODE / EDGE / BRANCH / ЗВТ

- Підтверджений символ обладнання → node із вашим type, position, rotation, назвою та інформаційною карткою.
- Підтверджена магістраль/лінія → edge з ортогональними points та прив'язками до портів; не вважати будь-який перетин підключенням.
- Відгалуження → branch із ОБОВ'ЯЗКОВИМ attachedTo: { type: "node" | "edge", id, ... }.
- ЗВТ → окремий елемент із branchId; координати та напрямок узгоджувати з кінцем branch.
- Кілька ЗВТ на одному branch — підтримувати вашим чинним правилом ланцюжка; після імпорту виконати перевірку цілісності всіх branchId/attachedTo.
- Написи та діаметри → не зливати в один рядок: назва — в інформаційну картку; технічні властивості — в універсальні параметри/JSON.
- Не вгадувати відсутні дані: залишати null і позначку needs-review.
- Генерувати стабільні ID тільки на етапі затвердження, зберігати відповідність tempId → id для аудиту та повторного імпорту.

7. ПІДКЛАДКА У KONVA: ТЕХНІЧНІ ДЕТАЛІ

- Зображення підкладки зберігати окремо від графа схеми; у стані тримати imageUrl/fileId, width, height, x, y, scaleX, scaleY, rotation, opacity, locked.
- Підкладку рендерити нижче об'єктів. У режимі редагування вимкнути її listening, щоб не перехоплювала кліки.
- Для великих сканів робити preview і тайли/фрагменти; не завантажувати без потреби весь 600 dpi аркуш у пам'ять браузера.
- Дві контрольні точки на скані та відповідні точки в схемі дають масштаб/поворот/зсув; за перспективних викривлень потрібна попередня rectification, а не проста трансформація Konva.
- Додати слайдер прозорості, клавішу швидкого приховування, порівняння «скан/об'єкти», сітку і snap, інструмент ортогонального трасування.
- Під час експорту готової цифрової схеми підкладку вимикати за замовчуванням, але залишати в історії проєкту.

8. ЯК ВИКОРИСТОВУВАТИ ШІ БЕЗ ЗАЙВИХ ПОМИЛОК

Пайплайн із двома проходами:
1) CV знаходить геометрію, OCR — написи, детектор — символи.
2) Мультимодальна модель отримує зображення фрагмента + результати першого проходу + каталог компонентів і пропонує семантичні відповідності та спірні зв'язки.
3) Детермінований код перевіряє координати, близькість до портів, допустимі типи, ортогональність, відсутність dangling references.
4) Людина підтверджує підсвічені сумнівні ділянки; після цього формується робочий JSON.

Для конфіденційних або чутливих схем перед використанням хмарного AI узгодити правила доступу і передачі даних. За потреби залишити OCR/CV і власний детектор локально, без передачі сканів стороннім сервісам.

9. ПЛАН ВПРОВАДЖЕННЯ

ЕТАП 1 — 1–2 ітерації: імпорт скану/PDF, вибір сторінки, підкладка, масштабування, калібрування, opacity, ручне трасування вашими компонентами. Зберігати transform і зв'язок схеми з аркушем.
ЕТАП 2 — 1–2 ітерації: OpenCV для прямих/кіл, OCR для написів, попередній JSON, напівпрозорі пропозиції, підтвердження по одному/групами.
ЕТАП 3 — пілот: каталог символів, 20–50 розмічених аркушів, шаблонне розпізнавання або власний детектор; тестування на відкладених альбомах.
ЕТАП 4 — AI: мультимодальна інтерпретація складних фрагментів, перевірка топології, рейтинг ділянок за потребою ручної перевірки.
ЕТАП 5 — масштабування: пакетний імпорт альбомів, черга, журнал помилок, версіонування, повторний запуск тільки змінених фрагментів.

10. КРИТЕРІЇ ПРИЙМАННЯ ПІЛОТУ

- На контрольному наборі порівняти ручне перенесення з режимом підкладки та режимом AI+CV; врахувати час виправлень.
- Виміряти пропущені символи, зайві символи, неправильні перетини/з'єднання, OCR-помилки і помилки прив'язки branch/ЗВТ.
- Встановити правило: жодна непідтверджена неоднозначна топологічна операція не потрапляє у фінальну схему.
- Перевірити імпорт/експорт без втрати інформаційної картки, параметрів, attachments та зв'язків.
- Додати можливість повернутися до фрагмента вихідного скану для кожного імпортованого об'єкта.

11. ПРАКТИЧНИЙ ВИСНОВОК

Спочатку зробіть якісну підкладку з ручним трасуванням — це найменший ризик і найшвидший шлях до користі. Паралельно збирайте виправлені користувачами схеми як еталонний датасет. Далі додавайте OCR і геометрію, потім власний детектор символів та мультимодальну модель для складних випадків. Ваші наявні компоненти Konva та правила node/edge/branch/ЗВТ мають бути єдиним джерелом правди для фінального JSON.
