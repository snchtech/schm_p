Так, ти правильно розумієш: JSON для повного відтворення схеми потрібно формувати з централізованого Zustand Store, але є важливий нюанс — зберігати весь Zustand Store безпосередньо не потрібно і навіть небажано.

Для твоєї системи Next.js + Konva + Oracle 21c я рекомендую розділити стан Zustand на дві категорії:

1. Document State — усе, що визначає вигляд, структуру, геометрію та властивості схеми. Це обов'язково зберігаємо в JSON.
2. Runtime/UI State — тимчасовий стан редактора: вибрані об'єкти, відкриті модальні вікна, режими інструментів, стан перетягування, завантаження, функції та посилання на Konva-об'єкти. Це не потрібно зберігати як частину схеми.

Причому Document State — це не тільки `nodes`, `edges` і `zvt`. Це також параметри самого полотна, шари, стилі, налаштування графічних елементів, прив'язки, примітки, таблиці специфікацій, розміщення файлів та інші дані, необхідні для відтворення документа.

## 2. Приклад структури Zustand Store для твоєї системи

Я б організував стан приблизно так:

```
const useEditorStore = create((set, get) => ({
  // 1. Дані документа
  document: {
    metadata: {
      documentType: "EQUIPMENT_SCHEME",
      format: "A3",
      orientation: "landscape",
    },

    canvas: {
      width: 1600,
      height: 1000,
      background: "#ffffff",
      gridSize: 10,
    },

    objects: {
      nodes: [],
      edges: [],
      zvt: [],
      branches: [],
      notes: [],
      callouts: [],
      specifications: [],
      images: [],
    },

    layers: [],
    styles: {},
  },

  // 2. Тимчасовий стан редактора

    selectedObjectIds: [],
```

Якщо зараз у тебе всі властивості знаходяться на одному рівні, наприклад `state.nodes`, `state.edges`, `state.zvt`, `state.selectedNode`, `state.gridSize`, `state.addNode`, це також нормально.

Можна створити окремий механізм експорту, який збере потрібні поля без зміни структури Store.

## 3. Як формувати JSON, не втрачаючи важливих властивостей

Я рекомендую створити файл:

`src/lib/schemeSnapshot.js`

І реалізувати в ньому окрему функцію.

```

const SNAPSHOT_SCHEMA_VERSION = 1;

export function createSchemeSnapshot(state) {
  return {
    schemaVersion: SNAPSHOT_SCHEMA_VERSION,

    metadata: {
      documentType: state.documentType,
      format: state.format,
      orientation: state.orientation,
    },

    canvas: {
      width: state.canvasWidth,
      height: state.canvasHeight,
      background: state.canvasBackground,
      gridSize: state.gridSize,
    },

    objects: {
      nodes: state.nodes,
      edges: state.edges,
      zvt: state.zvt,
      branches: state.branches,
      notes: state.notes,
      callouts: state.callouts,
      specifications: state.specifications,
      images: state.images,
    },

    layers: state.layers,
    styles: state.styles,
  };
}

```

Назви полів тут умовні — їх потрібно замінити відповідно до твого Zustand Store.

Зверни увагу: ми не перелічуємо кожну властивість NODE або EDGE окремо.

Якщо твій `node` має 40 властивостей, включно зі стилями, розмірами, позицією, поворотом, налаштуваннями інформаційної картки та прив'язками, усі вони потраплять у snapshot як частина об'єкта `node`.

Наприклад:

```
objects: {
  nodes: state.nodes
}
```

Тобто ти зберігаєш увесь масив об'єктів із вкладеними властивостями, а не тільки `id`, `x`, `y`.

Єдина умова: самі об'єкти мають бути JSON-сумісними. Якщо всередині є `ref`, `Map`, `Set`, функції, DOM-елементи чи екземпляри Konva, для них потрібне окреме перетворення або виключення.

## 4. Як не пропустити жодну частину Store

Це найважливіше питання у твоєму випадку.

Припустимо, зараз твій Zustand Store містить 100 властивостей. Якщо вручну вибрати тільки 20, можна випадково втратити налаштування, які впливають на відображення схеми.

Тому я пропоную спочатку зробити аудит усіх полів Zustand Store.

Ось невеликий діагностичний код:

```
const state = useEditorStore.getState();

console.table(
  Object.entries(state).map(([key, value]) => ({
    key,
    type: Array.isArray(value)
      ? "array"
      : typeof value,
    length: Array.isArray(value)
      ? value.length
      : null,
  }))
);
```

Цей код виведе список усіх властивостей верхнього рівня.

Після цього ми зможемо класифікувати їх.

| Приклад поля            | Зберігати?  | Причина                      |
| ----------------------- | ----------- | ---------------------------- |
| `nodes`, `edges`        | Так         | Геометрія та об'єкти         |
| `zvt`, `branches`       | Так         | Структура ЗВТ                |
| `specifications`        | Так         | Таблиці специфікацій         |
| `layers`                | Так         | Порядок відображення         |
| `gridSize`              | Так         | Налаштування документа       |
| `selectedNodeId`        | Ні          | Тимчасове виділення          |
| `isDragging`            | Ні          | Стан взаємодії               |
| `activeTool`            | Ні          | Інструмент редактора         |
| `addNode`, `updateEdge` | Ні          | Функції                      |
| `stageRef`              | Ні          | Посилання на Konva           |
| `undoStack`             | Зазвичай ні | Локальна історія редагування |

Для вкладених структур потрібна додаткова перевірка. Не варто покладатися лише на `JSON.stringify(state)`, оскільки він може непомітно пропустити функції або некоректно серіалізувати спеціальні типи.

## 5. Як зберігати Snapshot через Zustand

Коли ми визначили повний набір полів документа, можна додати метод експорту.

```
export const exportSchemeSnapshot = () => {
  const state = useEditorStore.getState();

  const snapshot = createSchemeSnapshot(state);

  return JSON.stringify(snapshot);
};
```

Далі кнопка збереження:

```
async function handleSave() {
  const snapshotJson = exportSchemeSnapshot();

  const response = await fetch(
    `/api/documents/${versionId}/snapshot`,
    {
      method: "PUT",
      headers: {
        "Content-Type": "application/json",
      },
      body: JSON.stringify({
        snapshot: JSON.parse(snapshotJson),
        baseRevision: saveRevision,
      }),
    }
  );

  if (!response.ok) {
    throw new Error("Помилка збереження");
  }

  const result = await response.json();

  // Оновити saveRevision після успішного COMMIT
  return result;
}
```

Тут `versionId` — ідентифікатор DRAFT, а `saveRevision` — номер останнього успішного збереження. Сервер повинен перевіряти його та повертати нове значення.

JSON Snapshot передається в Oracle як CLOB. Пізніше цей самий документ можна завантажити назад у Zustand.

## 6. Як правильно відновлювати Zustand Store

Ось тут я рекомендую бути особливо уважним.

Не варто робити:

```
useEditorStore.setState(snapshot);
```

Це може перезаписати службові поля, залишити частину попереднього документа або порушити структуру Store.

Краще створити спеціальний метод імпорту.

```
function restoreSchemeSnapshot(snapshot) {
  if (snapshot.schemaVersion !== 1) {
    throw new Error("Непідтримувана версія JSON");
  }

  const documentState = {
    documentType: snapshot.metadata.documentType,
    format: snapshot.metadata.format,
    orientation: snapshot.metadata.orientation,

    canvasWidth: snapshot.canvas.width,
    canvasHeight: snapshot.canvas.height,
    canvasBackground: snapshot.canvas.background,
    gridSize: snapshot.canvas.gridSize,

    nodes: snapshot.objects.nodes,
    edges: snapshot.objects.edges,
    zvt: snapshot.objects.zvt,
    branches: snapshot.objects.branches,
    notes: snapshot.objects.notes,
    callouts: snapshot.objects.callouts,
    specifications: snapshot.objects.specifications,
    images: snapshot.objects.images,

    layers: snapshot.layers,
    styles: snapshot.styles,

    // Скидаємо тимчасові стани
    selectedNodeId: null,
    selectedEdgeId: null,
    isDragging: false,
    activeTool: "select",
  };

  useEditorStore.setState(documentState);
}
```

Це приклад для плоскої структури Store. Перед застосуванням потрібно перевірити всі поля й виконати валідацію snapshot.

Якщо згодом структура JSON зміниться, наприклад `schemaVersion: 2`, додамо функцію міграції зі старого формату.

## 7. Що ще потрібно врахувати для повного відтворення Konva

Для твого редактора є кілька особливо важливих аспектів.

Геометрія: якщо координати `EDGE`, `ZVT_BRANCH` або anchor points розраховуються функціями, потрібно вирішити, чи зберігаємо кінцеву геометрію, чи тільки вхідні параметри алгоритму. Я рекомендую зберігати і параметри, і необхідну кінцеву геометрію, щоб старі схеми відкривалися без візуальних змін.

Графічні файли: PDF, SVG, PNG та інші вкладення краще зберігати окремо. У snapshot повинні бути їхні `assetId`, координати, розміри, трансформації та налаштування відображення. Після завантаження Zustand застосунок окремо отримує файли за ID.

Послідовність шарів: порядок об'єктів має відновлюватися так само, як до збереження. Особливо це важливо для підкладок, ліній і ЗВТ.

Інформаційні картки: якщо дані карток є частиною об'єктів, вони повинні входити в snapshot. При подальшій синхронізації з реляційними таблицями Oracle необхідно визначити єдине джерело істини для кожного поля.

Завантаження: усі дані документа краще встановлювати в Zustand одним атомарним оновленням. Після цього React-Konva відтворює сцену, а асинхронні ресурси завантажуються окремо.

## 8. Яку архітектуру я рекомендую в підсумку

Централізований Zustand Store

Document State

Усі дані, необхідні для відтворення схеми

UI / Runtime State

Інструменти, виділення, refs, методи

Snapshot Serializer / Deserializer

Oracle 21c — DOC_SNAPSHOT

Моя рекомендація — не створювати другий Zustand Store тільки для збереження. Залишай свій централізований Store, але винеси формування та відновлення JSON в окремий модуль `schemeSnapshot.js`.

Це дасть можливість змінювати структуру редактора, не прив'язуючи безпосередньо всі його внутрішні поля до формату БД.

### Що пропоную зробити далі

Надішли мені файл твого централізованого Zustand Store (або декілька файлів, якщо він розбитий на slices).

Я зможу розібрати кожне поле та підготувати для тебе конкретну реалізацію `exportSnapshot()` і `importSnapshot()` без втрати `NODE`, `EDGE`, `ZVT`, `BRANCH`, специфікацій, стилів, координат, налаштувань та інших об'єктів.

Тоді отримаємо не умовний приклад, а код, який можна буде інтегрувати безпосередньо в твій проєкт.
