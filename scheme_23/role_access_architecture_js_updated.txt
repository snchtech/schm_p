ОНОВЛЕНИЙ ПАКЕТ ДОПРАЦЮВАНЬ
АРХІТЕКТУРА РОЛЕВОЇ СИСТЕМИ ТА КЕРУВАННЯ ДОСТУПОМ
для проєкту «Альбом схем»
JavaScript + Feature-Sliced Design + Zustand

======================================================================
1. МЕТА
======================================================================

Побудувати централізовану систему доступів без зміни поточної
Feature-Sliced Design архітектури проєкту.

Система повинна:

- працювати на JavaScript, без TypeScript;
- підтримувати ролі reader, editor, administrator;
- дозволяти користувачу мати декілька ролей;
- об’єднувати permissions усіх ролей користувача;
- підтримувати scope: global, department, album, albumPage, scheme;
- дозволяти editor перемикатися між режимом перегляду та редагування;
- показувати в шапці поточний статус:
  «Режим перегляду»,
  «Режим редагування»,
  «Режим адміністрування»;
- для користувача лише з роллю reader не показувати перемикач,
  а показувати тільки статус «Режим перегляду»;
- для editor показувати перемикач view/edit;
- для administrator показувати статус «Режим адміністрування»;
- централізовано перевіряти права в UI, controller/store та API;
- у майбутньому підключити БД без перебудови frontend.

======================================================================
2. ГОЛОВНА ІДЕЯ
======================================================================

Потрібно розділити:

1. РОЛЬ — що користувачу взагалі дозволено.
2. PERMISSION — конкретна дозволена дія.
3. SCOPE — де саме діє роль.
4. WORKSPACE MODE — у якому режимі користувач зараз працює.

Приклад:

Користувач має роль editor у своєму відділі.

Це означає, що він МАЄ ПРАВО редагувати.

Але схема може бути відкрита в режимі view.

Тоді:

- право на редагування є;
- але зараз редагування тимчасово вимкнено;
- користувач може натиснути «Редагувати» в шапці;
- після цього активується edit mode.

Формула:

canEditNow =
  користувач має permission
  &&
  workspaceMode === "edit"

======================================================================
3. ЯК ПРАЦЮЮТЬ ДЕКІЛЬКА РОЛЕЙ
======================================================================

Якщо користувач має декілька ролей, permissions цих ролей об’єднуються.

Наприклад:

roles: ["reader", "editor"]

reader дає:

- scheme.view;
- scheme.exportPdf.

editor дає:

- scheme.view;
- scheme.update;
- drawing.node.create;
- drawing.node.update;
- drawing.node.delete.

Результат:

- scheme.view;
- scheme.exportPdf;
- scheme.update;
- drawing.node.create;
- drawing.node.update;
- drawing.node.delete.

Тобто в одному scope editor фактично перекриває reader,
оскільки editor уже має права на перегляд.

Але дві ролі мають сенс, якщо вони діють у різних scope.

Приклад:

- editor у department-electric;
- reader у department-water.

Тоді:

- у department-electric користувач може редагувати;
- у department-water користувач може лише переглядати.

8. ПЕРЕВІРКА SCOPE
======================================================================

Файл:

src/features/auth/model/accessPolicy.js

Код:

import { ROLE_PERMISSIONS } from "./rolePermissions";

function roleHasPermission(roleId, permission) {
  const rolePermissions =
    ROLE_PERMISSIONS[roleId] || [];

  return rolePermissions.includes(permission);
}

function assignmentMatchesResource(
  assignment,
  resource
) {
  if (!assignment || !assignment.scope) {
    return false;
  }

  if (assignment.scope.type === "global") {
    return true;
  }

  if (!resource) {
    return false;
  }

  switch (assignment.scope.type) {
    case "department":
      return (
        assignment.scope.id
        === resource.departmentId
      );

    case "album":
      return (
        assignment.scope.id
          === resource.albumId
        || (
          resource.type === "album"
          && assignment.scope.id
            === resource.id
        )
      );

    case "albumPage":
      return (
        assignment.scope.id
          === resource.albumPageId
        || (
          resource.type === "albumPage"
          && assignment.scope.id
            === resource.id
        )
      );

    case "scheme":
      return (
        assignment.scope.id
          === resource.schemeId
        || (
          resource.type === "scheme"
          && assignment.scope.id
            === resource.id
        )
      );

    default:
      return false;
  }
}

export function can(
  user,
  permission,
  resource
) {
  if (
    !user
    || !Array.isArray(user.roleAssignments)
  ) {
    return false;
  }

  return user.roleAssignments.some(
    (assignment) => {
      const allowedByRole =
        roleHasPermission(
          assignment.roleId,
          permission
        );

      const allowedInScope =
        assignmentMatchesResource(
          assignment,
          resource
        );

      return (
        allowedByRole
        && allowedInScope
      );
    }
  );
}

export function getEffectivePermissions(
  user,
  resource
) {
  if (
    !user
    || !Array.isArray(user.roleAssignments)
  ) {
    return [];
  }

  const permissions =
    user.roleAssignments.flatMap(
      (assignment) => {
        const matches =
          assignmentMatchesResource(
            assignment,
            resource
          );

        if (!matches) {
          return [];
        }

        return (
          ROLE_PERMISSIONS[
            assignment.roleId
          ] || []
        );
      }
    );

  return [...new Set(permissions)];
}

export function hasRole(
  user,
  roleId,
  resource
) {
  if (
    !user
    || !Array.isArray(user.roleAssignments)
  ) {
    return false;
  }

  return user.roleAssignments.some(
    (assignment) => {
      return (
        assignment.roleId === roleId
        && assignmentMatchesResource(
          assignment,
          resource
        )
      );
    }
  );
}

9. ЧОМУ РЕЖИМ РОБОТИ НЕ Є РОЛЛЮ
======================================================================

Роль editor означає:

«Користувачу дозволено редагування».

Режим view означає:

«Користувач зараз добровільно працює без редагування».

Режим edit означає:

«Користувач зараз використовує своє право на редагування».

Роль reader:

- не може перейти в edit;
- завжди працює в view;
- бачить статус «Режим перегляду».

Роль editor:

- може перемикатися view/edit;
- за замовчуванням відкриває схему у view;
- у view не може змінювати документ;
- у edit може змінювати документ.

Роль administrator:

- бачить статус «Режим адміністрування»;
- адміністративний статус має пріоритет;
- за потреби administrator може мати окремий режим canvas,
  але в шапці відображається саме «Режим адміністрування».

10. useAuthStore
======================================================================

Файл:

src/features/auth/model/useAuthStore.js

Код:

import { create } from "zustand";
import { MOCK_USERS } from "./mockUsers";

export const ACCESS_MODES = {
  VIEW: "view",
  EDIT: "edit",
  ADMIN: "admin",
};

export const useAuthStore = create(
  (set, get) => ({
    currentUser: null,
    activeDepartmentId: null,
    workspaceMode: ACCESS_MODES.VIEW,
    isInitialized: false,

    setCurrentUser: (currentUser) => {
      const hasAdministratorRole =
        currentUser?.roleAssignments?.some(
          (assignment) =>
            assignment.roleId
              === "administrator"
        );

      set({
        currentUser,
        activeDepartmentId:
          currentUser?.departmentIds?.[0]
          || null,

        workspaceMode:
          hasAdministratorRole
            ? ACCESS_MODES.ADMIN
            : ACCESS_MODES.VIEW,

        isInitialized: true,
      });
    },

    setActiveDepartmentId: (
      activeDepartmentId
    ) => {
      set({ activeDepartmentId });
    },

    setWorkspaceMode: (
      workspaceMode
    ) => {
      set({ workspaceMode });
    },

    resetWorkspaceMode: () => {
      const currentUser =
        get().currentUser;

      const hasAdministratorRole =
        currentUser?.roleAssignments?.some(
          (assignment) =>
            assignment.roleId
              === "administrator"
        );

      set({
        workspaceMode:
          hasAdministratorRole
            ? ACCESS_MODES.ADMIN
            : ACCESS_MODES.VIEW,
      });
    },

    initializeAuth: () => {
      // Тимчасово без БД.
      // Для тесту можна змінити:
      // MOCK_USERS.reader
      // MOCK_USERS.editor
      // MOCK_USERS.mixed
      // MOCK_USERS.administrator

      get().setCurrentUser(
        MOCK_USERS.editor
      );
    },

    logout: () => {
      set({
        currentUser: null,
        activeDepartmentId: null,
        workspaceMode:
          ACCESS_MODES.VIEW,
        isInitialized: false,
      });
    },
  })
);

Примітка:

У строгому поділі відповідальності workspaceMode можна зберігати
в useCanvasStore або useWorkspaceStore.

Але для початкової реалізації допустимо тримати його в useAuthStore,
тому що:

- він безпосередньо пов’язаний із поточним режимом доступу;
- всі компоненти шапки отримують дані з одного store;
- простіше впровадити без перебудови поточного проєкту.

У майбутньому mode можна винести без зміни can().

import { ACCESS_MODES } from "./useAuthStore";
import {
  can,
  hasRole,
} from "./accessPolicy";
import { PERMISSIONS } from "./permissions";

export function canEnterEditMode(
  user,
  resource
) {
  return can(
    user,
    PERMISSIONS.SCHEME_UPDATE,
    resource
  );
}

export function isAdministrator(
  user,
  resource
) {
  return hasRole(
    user,
    "administrator",
    resource
  );
}

export function canEditNow(
  user,
  resource,
  workspaceMode
) {
  return (
    workspaceMode === ACCESS_MODES.EDIT
    && can(
      user,
      PERMISSIONS.SCHEME_UPDATE,
      resource
    )
  );
}

export function getAccessModeStatus({
  user,
  resource,
  workspaceMode,
}) {
  if (
    isAdministrator(
      user,
      resource
    )
  ) {
    return {
      key: "admin",
      label:
        "Режим адміністрування",
    };
  }

  const allowedToEdit =
    canEnterEditMode(
      user,
      resource
    );

  if (
    allowedToEdit
    && workspaceMode
      === ACCESS_MODES.EDIT
  ) {
    return {
      key: "edit",
      label:
        "Режим редагування",
    };
  }

  return {
    key: "view",
    label:
      "Режим перегляду",
  };
}

12. БЕЗПЕЧНА ЗМІНА РЕЖИМУ
======================================================================

Не можна просто дозволити будь-кому зробити:

setWorkspaceMode("edit")

Потрібна централізована перевірка.

Додати в useAuthStore:

import { can } from "./accessPolicy";
import { PERMISSIONS } from "./permissions";

requestWorkspaceMode: (
  nextMode,
  resource
) => {
  const {
    currentUser,
  } = get();

  const hasAdministratorRole =
    currentUser?.roleAssignments?.some(
      (assignment) =>
        assignment.roleId
          === "administrator"
    );

  if (hasAdministratorRole) {
    set({
      workspaceMode:
        ACCESS_MODES.ADMIN,
    });

    return true;
  }

  if (
    nextMode
      === ACCESS_MODES.VIEW
  ) {
    set({
      workspaceMode:
        ACCESS_MODES.VIEW,
    });

    return true;
  }

  if (
    nextMode
      === ACCESS_MODES.EDIT
  ) {
    const allowed = can(
      currentUser,
      PERMISSIONS.SCHEME_UPDATE,
      resource
    );

    if (!allowed) {
      return false;
    }

    set({
      workspaceMode:
        ACCESS_MODES.EDIT,
    });

    return true;
  }

  return false;
},

    resetWorkspaceMode: () => {
      const currentUser =
        get().currentUser;

      const hasAdministratorRole =
        currentUser?.roleAssignments?.some(
          (assignment) =>
            assignment.roleId
              === "administrator"
        );

      set({
        workspaceMode:
          hasAdministratorRole
            ? ACCESS_MODES.ADMIN
            : ACCESS_MODES.VIEW,
      });
    },

    initializeAuth: () => {
      get().setCurrentUser(
        MOCK_USERS.editor
      );
    },

    logout: () => {
      set({
        currentUser: null,
        activeDepartmentId: null,
        workspaceMode:
          ACCESS_MODES.VIEW,
        isInitialized: false,
      });
    },
  })
);

  } = useAuthStore.getState();

export function assertCanMutate(

======================================================================
28. ПОВЕДІНКА READER
======================================================================

Reader:

- завжди отримує workspaceMode = "view";
- не бачить перемикач;
- бачить статус «Режим перегляду»;
- не може вручну встановити edit через requestWorkspaceMode;
- може виконувати тільки свої permissions;
- може переглядати доступні схеми;
- може взаємодіяти з UI, який не змінює документ.

======================================================================
29. ПОВЕДІНКА EDITOR
======================================================================

Editor:

- після входу отримує workspaceMode = "view";
- у header бачить перемикач;
- у view mode:
  - схема read-only;
  - кнопки мутацій приховані/disabled;
  - pan/zoom/view працюють;
- після переходу в edit:
  - доступні дозволені editing actions;
- може повернутися у view без втрати ролі.

30. ПОВЕДІНКА КОРИСТУВАЧА З ДВОМА РОЛЯМИ
======================================================================

Варіант 1:

editor + reader в одному department.

Результат:

- permissions об’єднуються;
- користувач має право редагувати;
- у header бачить view/edit;
- reader не обмежує editor.

Варіант 2:

editor у department-electric,
reader у department-water.

Коли відкрито scheme з department-electric:

- canEnterEditMode = true;
- показується view/edit switch.

Коли відкрито scheme з department-water:

- canEnterEditMode = false;
- switch зникає;
- показується «Режим перегляду»;
- workspaceMode потрібно автоматично скинути у view.

Приклад hook на сторінці схеми:

import { useEffect } from "react";
import {
  ACCESS_MODES,
  PERMISSIONS,
  can,
  useAuthStore,
} from "@/features/auth";

export function useSyncAccessMode(
  resource
) {
  const currentUser =
    useAuthStore(
      (state) =>
        state.currentUser
    );

  const workspaceMode =
    useAuthStore(
      (state) =>
        state.workspaceMode
    );

  const requestWorkspaceMode =
    useAuthStore(
      (state) =>
        state.requestWorkspaceMode
    );

  useEffect(() => {
    if (!resource) {
      return;
    }

    const canEditResource =
      can(
        currentUser,
        PERMISSIONS.SCHEME_UPDATE,
        resource
      );

    if (
      !canEditResource
      && workspaceMode
        === ACCESS_MODES.EDIT
    ) {
      requestWorkspaceMode(
        ACCESS_MODES.VIEW,
        resource
      );
    }
  }, [
    currentUser,
    resource,
    workspaceMode,
    requestWorkspaceMode,
  ]);
}

На сторінці:

useSyncAccessMode(
  schemeResource
);

Сценарій:

1. Користувач редагує електричну схему.
2. Переходить на водну схему.
3. Там він лише reader.
4. Hook автоматично переводить mode у view.
5. Header показує «Режим перегляду».
6. Editing toolbar вимикається.

======================================================================

Frontend permissions потрібні для UX.

API flow:

1. Визначити current user із сесії.

3. Завантажити resource з БД.
4. Побудувати access resource.

- ролям із Zustand;

40. ПІДСУМКОВА ЛОГІКА HEADER
======================================================================

Reader:

- статус: «Режим перегляду»;
- switch: відсутній.

Editor:

- за замовчуванням: «Режим перегляду»;
- switch: Перегляд / Редагування;
- після перемикання:
  «Режим редагування».

Administrator:

- статус:
  «Режим адміністрування»;
- switch view/edit:
  не показується;
- доступ до адміністративного UI:
  через permissions.

Editor + reader в одному scope:

- показується editor поведінка;
- permissions об’єднуються;
- доступний switch.

Editor у scope A + reader у scope B:

- у scope A:
  доступний switch;
- у scope B:
  тільки «Режим перегляду»;
- при переході A → B edit автоматично скидається у view.

======================================================================
41. ГОЛОВНА РЕКОМЕНДАЦІЯ
======================================================================

Основною одиницею перевірки має бути permission.

Role лише групує permissions.

Scope визначає, де діє роль.

useAuthStore зберігає:

- currentUser;
- roleAssignments;
- activeDepartmentId;
- workspaceMode;
- auth initialization.

can() визначає:

- чи є permission;
- чи діє роль для resource.

workspaceMode визначає:

- чи користувач зараз переглядає;
- чи користувач зараз редагує;
- чи користувач перебуває в admin mode.

Для мутації потрібно:

can(user, permission, resource)
&&
workspaceMode дозволяє mutation.

Цей підхід:

- не змінює FSD;
- працює на JavaScript;
- підтримує декілька ролей;
- дозволяє безпечний view/edit режим;
- дозволяє виводити статус у header;
- готовий до майбутньої БД;
- не потребує повного переписування проєкту.
