АРХІТЕКТУРА РОЛЕВОЇ СИСТЕМИ ТА КЕРУВАННЯ ДОСТУПОМ
для проєкту «Альбом схем»

1. МЕТА

Побудувати централізовану, масштабовану та придатну до подальшого підключення БД систему доступів, яка дозволяє:

- підтримувати ролі reader, editor, administrator та нові ролі в майбутньому;
- призначати користувачу декілька ролей одночасно;
- обмежувати доступ не лише роллю, а й відділом, посадою та конкретним ресурсом;
- визначати різний склад панелі інструментів для різних відділів;
- повторно використовувати спільні графічні елементи без дублювання;
- визначати доступ до альбомів, сторінок, схем і графічних об’єктів;
- централізовано перевіряти права в UI, controller/store та API;
- у майбутньому без зміни основної архітектури перейти від статичної конфігурації до даних з БД.

2. КЛЮЧОВЕ АРХІТЕКТУРНЕ РІШЕННЯ

Не варто будувати систему лише на перевірках виду:

if (role === "editor") { ... }

Такий підхід швидко перестає масштабуватися, оскільки:

- користувач може мати декілька ролей;
- одна роль може діяти лише в межах конкретного альбому або відділу;
- однакові ролі можуть мати різні дозволи в різних контекстах;
- посада і відділ можуть впливати на доступ;
- administrator не завжди повинен мати доступ до абсолютно всього;
- частина функціоналу може бути доступною reader, наприклад export PDF;
- різним відділам потрібні різні набори інструментів.

Рекомендована модель:

RBAC + Resource Scope + Attributes

де:

- RBAC — ролі та дозволи;
- Resource Scope — область, у межах якої діє роль;
- Attributes — додаткові умови: відділ, посада, власник, тип ресурсу тощо.

3. БАЗОВІ ПОНЯТТЯ

3.1. Permission

3.2. Role

Role — іменований набір дозволів.

Початкові ролі:

reader
editor
administrator

Але роль не повинна бути основною умовою в компонентах. Компоненти повинні перевіряти permission.

Правильно:

can("drawing.node.create")

Неправильно:

role === "editor"

3.3. Scope

Scope — контекст, у межах якого діє роль або дозвіл.

Рекомендовані типи scope:

global
department
album
albumPage
scheme

Приклад:

користувач може бути:
- editor у department A;
- reader у department B;
- administrator лише для одного album;
- editor конкретної scheme.

3.4. Attribute

Attribute — додаткові характеристики користувача або ресурсу.

Для користувача:

user.id
user.departmentIds
user.positionIds
user.status

Для ресурсу:

resource.departmentId
resource.albumId
resource.ownerId
resource.type
resource.visibility

Attributes потрібні для правил виду:

- користувач бачить альбоми свого відділу;
- керівник відділу бачить усі альбоми відділу;
- автор схеми може її редагувати;
- користувач певної посади може погоджувати схему;
- інші відділи можна переглядати, але вони початково згорнуті.

Користувач може мати декілька roleAssignments.

Результат:

- в електротехнічному відділі користувач редагує;
- у водному відділі користувач лише переглядає;
- ролі не конфліктують, оскільки діють у різних scope.

8. ПОЛІТИКА ДОСТУПУ

// src/auth/policy.ts

import { ROLE_PERMISSIONS } from "./permissions";
import type {
  AccessResource,
  AuthUser,
  Permission,
  RoleAssignment,
} from "./types";

function roleHasPermission(
  roleId: RoleAssignment["roleId"],
  permission: Permission,
): boolean {
  return ROLE_PERMISSIONS[roleId].includes(permission);
}

function assignmentMatchesResource(
  assignment: RoleAssignment,
  resource?: AccessResource,
): boolean {
  if (assignment.scope.type === "global") {
    return true;
  }

  if (!resource) {
    return false;
  }

  switch (assignment.scope.type) {
    case "department":
      return assignment.scope.id === resource.departmentId;

    case "album":
      return assignment.scope.id === resource.albumId
        || (
          resource.type === "album"
          && assignment.scope.id === resource.id
        );

    case "albumPage":
      return assignment.scope.id === resource.albumPageId
        || (
          resource.type === "albumPage"
          && assignment.scope.id === resource.id
        );

    case "scheme":
      return assignment.scope.id === resource.schemeId
        || (
          resource.type === "scheme"
          && assignment.scope.id === resource.id
        );

    default:
      return false;
  }
}

export function can(
  user: AuthUser | null,
  permission: Permission,
  resource?: AccessResource,
): boolean {
  if (!user) {
    return false;
  }

  return user.roleAssignments.some((assignment) => {
    return (
      roleHasPermission(assignment.roleId, permission)
      && assignmentMatchesResource(assignment, resource)
    );
  });
}

9. ДОСТУПИ ЗА ПОСАДАМИ

Посаду не варто безпосередньо змішувати з роллю.

Краще підтримувати окремі policy rules або position grants.

Приклад:

// src/auth/positionPermissions.ts

export const POSITION_PERMISSIONS = {
  "chief-engineer": [
    "scheme.view",
    "scheme.update",
    "scheme.exportPdf",
  ],

  "department-head": [
    "album.view",
    "album.update",
    "album.manageMembers",
    "scheme.view",
    "scheme.update",
  ],
} as const;

Після цього can() може об’єднувати:

- permissions з ролей;
- permissions з посад;
- персональні override;
- заборони.

Рекомендований порядок обчислення:

1. explicit deny;
2. global administrator permissions;
3. role permissions;
4. position permissions;
5. personal allow override;
6. contextual conditions.

Explicit deny має бути сильнішим за allow.

10. PERSONAL OVERRIDES

У майбутній БД можна передбачити винятки:

export interface PermissionOverride {
  permission: Permission;
  effect: "allow" | "deny";
  scope: AccessScope;
}

Приклад:

- editor відділу;
- але заборонено scheme.delete;
- дозволено album.manageMembers лише в одному альбомі.

Не слід використовувати override як основний механізм.
Вони потрібні лише для винятків.

11.4. Фільтрація панелі

export function getAvailableToolboxItems(params: {
  user: AuthUser;
  departmentId: string;
  schemeId: string;
}) {
  const profile = DEPARTMENT_TOOLBOX_PROFILES.find(
    (item) => item.departmentId === params.departmentId,
  );

  if (!profile) {
    return [];
  }

  const resource: AccessResource = {
    type: "scheme",
    id: params.schemeId,
    schemeId: params.schemeId,
    departmentId: params.departmentId,
  };

  return TOOLBOX_ITEMS.filter((item) => {
    return (
      profile.itemIds.includes(item.id)
      && item.isActive
      && can(
        params.user,
        item.requiredPermission,
        resource,
      )
    );
  });
}

Результат визначається двома незалежними умовами:

1. елемент дозволений для відділу;
2. користувач має permission на використання елемента.

Це важливо, тому що:

- відділ визначає доступний каталог;
- роль визначає, що користувач може з ним робити.

Reader може бачити список інструментів або легенду, але не мати toolbox.useItem.
Editor може бачити й використовувати інструменти.

12. РОЗДІЛЕННЯ AUTH STORE І CANVAS STORE

Не варто зберігати повну рольову модель у useCanvasStore.

Рекомендовано:

useAuthStore:
- currentUser;
- roleAssignments;
- department context;
- access checks;
- permissions snapshot.

useCanvasStore:
- nodes;
- edges;
- selection;
- viewport;
- activeTool;
- document state;
- editor state.

Приклад:

// src/stores/useAuthStore.ts

interface AuthState {
  currentUser: AuthUser | null;
  activeDepartmentId: string | null;
  setCurrentUser: (user: AuthUser | null) => void;
  setActiveDepartmentId: (id: string | null) => void;
}

Canvas не повинен знати, як обчислюються ролі.
Він повинен отримувати результат can(...).

13. ЗАХИСТ НА ТРЬОХ РІВНЯХ

13.1. UI

UI приховує або блокує недоступні дії.

const allowed = can(
  currentUser,
  "drawing.node.create",
  currentSchemeResource,
);

<Button disabled={!allowed}>
  Додати елемент
</Button>

Це лише UX.
UI не є реальною межею безпеки.

13.2. Controller / Store

Controller має перевіряти permission перед мутацією.

function addNode(node: Node) {
  const user = useAuthStore.getState().currentUser;
  const canvas = useCanvasStore.getState();

  if (!can(
    user,
    "drawing.node.create",
    canvas.currentSchemeResource,
  )) {
    throw new AccessDeniedError(
      "drawing.node.create",
    );
  }

  canvas.addNodeInternal(node);
}

Store також може мати захисний wrapper для document mutations.

13.3. API / Server

Справжня перевірка доступу повинна відбуватись на сервері.

API не має довіряти:

- ролям з Zustand;
- disabled кнопці;
- даним, надісланим клієнтом;
- departmentId, який передав клієнт без перевірки.

На API потрібно:

1. визначити користувача із сесії або токена;
2. завантажити його role assignments;
3. завантажити ресурс;
4. побудувати AccessResource;
5. виконати can();
6. лише тоді виконувати операцію.

14. GLOBAL READ-ONLY ДЛЯ CANVAS

Підхід із глобальним read-only корисний, але він не повинен повністю замінювати permissions.

Причина:

reader може мати право:
- переглядати;
- масштабувати;
- переміщати viewport;
- вибирати об’єкти;
- відкривати картку;
- експортувати PDF.

Але не може:
- створювати;
- змінювати;
- видаляти;
- пересувати об’єкти;
- зберігати JSON.

Тому варто розділити:

document state — захищений permissions;
editor state — доступний для reader.

Приклад wrapper:

function createGuardedDocumentSet(
  set: StoreApi<CanvasState>["setState"],
  get: StoreApi<CanvasState>["getState"],
) {
  return (
    permission: Permission,
    producer: (
      state: CanvasState,
    ) => Partial<CanvasState>,
  ) => {
    const user = useAuthStore.getState().currentUser;
    const resource = get().currentSchemeResource;

    if (!can(user, permission, resource)) {
      throw new AccessDeniedError(permission);
    }

    set(producer);
  };
}

У store:

addNode: (node) =>
  setDocument(
    "drawing.node.create",
    (state) => ({
      nodes: [...state.nodes, node],
    }),
  ),

moveNode: (nodeId, position) =>
  setDocument(
    "drawing.object.move",
    (state) => ({
      nodes: state.nodes.map((node) =>
        node.id === nodeId
          ? { ...node, position }
          : node
      ),
    }),
  ),

setSelection: (selection) =>
  set({ selection }),

setViewport: (viewport) =>
  set({ viewport }),

Краще перевіряти окремі можливості:

const canMoveObject = can(

16. ДОСТУП ДО АЛЬБОМІВ СХЕМ

Потрібно розділити:

1. чи бачить користувач альбом;
2. як альбоми групуються та відкриваються в UI;
3. чи може користувач редагувати альбом.

Приклад моделі:

interface Album {
  id: string;
  name: string;
  departmentId: string;
  visibility: "department" | "shared" | "private";
  ownerId: string;
}

Алгоритм:

1. отримати всі альбоми, доступні користувачу через album.view;
2. згрупувати їх за departmentId;
3. відділ користувача показати першим;
4. його групу розгорнути;
5. інші доступні відділи показати згорнутими;
6. недоступні альбоми взагалі не повертати з API.

UI-стан розгортання не є permission.

Приклад:

const defaultExpandedDepartmentIds =
  currentUser.departmentIds;

Для кожної групи:

{
  departmentId,
  departmentName,
  isExpandedByDefault:
    currentUser.departmentIds.includes(
      departmentId,
    ),
  albums,
}

Якщо administrator має глобальний album.view, він бачить усі групи.
За замовчуванням можна розгортати:
- його власний відділ;
- або всі відділи, якщо це вимога продукту.

electricDepartmentEditor

21. REACT HOOK

// src/auth/hooks.ts

export function useCan(
  permission: Permission,
  resource?: AccessResource,
): boolean {
  const user = useAuthStore(
    (state) => state.currentUser,
  );

  return useMemo(
    () => can(user, permission, resource),
    [user, permission, resource],
  );
}

Використання:

const canEditScheme = useCan(
  "scheme.update",
  currentSchemeResource,
);

22. КОМПОНЕНТ GUARD

interface CanProps {
  permission: Permission;
  resource?: AccessResource;
  fallback?: React.ReactNode;
  children: React.ReactNode;
}

export function Can({
  permission,
  resource,
  fallback = null,
  children,
}: CanProps) {
  const allowed = useCan(
    permission,
    resource,
  );

  return allowed ? children : fallback;
}

Використання:

<Can
  permission="scheme.update"
  resource={currentSchemeResource}
>
  <EditSchemeButton />
</Can>

Цей компонент корисний для UI, але не замінює controller/API guard.

26. ПРАВИЛА ПРІОРИТЕТУ

Рекомендовано зафіксувати такі правила:

1. відсутність дозволу = deny;
2. explicit deny сильніший за allow;
3. role assignment діє лише в межах scope;
4. дочірній ресурс успадковує доступ від батьківського scope;
5. більш вузький deny може перекрити ширший allow;
6. administrator не обходить explicit deny автоматично, якщо це не визначено окремо;
7. UI ніколи не є джерелом істини;
8. дані про доступ не беруться з параметрів запиту без серверної перевірки.

27. ПРИКЛАД УСПАДКУВАННЯ SCOPE

Роль editor на album:

- дозволяє редагувати album;
- дозволяє редагувати albumPage цього album;
- дозволяє редагувати scheme в цих albumPage.

Роль reader на scheme:

- дає перегляд лише цієї scheme;
- не дає доступ до сусідніх схем;
- не дає редагування album.

Для цього resource має містити повний ланцюг:

departmentId
albumId
albumPageId
schemeId

28. НЕ РЕКОМЕНДОВАНІ РІШЕННЯ

Не робити:

- перевірки role === "reader" у десятках компонентів;
- окремий список графічних об’єктів для кожного відділу;
- копії однакових інструментів у різних відділах;
- зберігання ролі лише в canvas store;
- довіру до client-side role;
- одну глобальну роль без scope;
- створення ролі для кожної комбінації відділу і посади;
- лише hide/disable без controller/API guard;
- автоматичний повний доступ administrator без каталогу permissions;
- змішування UI state, document state та access state.

32. ГОЛОВНА РЕКОМЕНДАЦІЯ

Основною одиницею перевірки має бути не роль, а permission.

Роль повинна бути лише способом згрупувати permissions.

Відділ, альбом, сторінка та схема повинні визначати scope.

Посада повинна додавати окремі permissions або contextual rules.

Панель інструментів повинна будуватися з одного глобального каталогу через набори та профілі відділів.

Така модель дозволить:

- додавати нові ролі без переписування компонентів;
- комбінувати декілька ролей;
- видавати ролі на рівні БД;
- підтримувати різні права в різних відділах;
- не дублювати графічні елементи;
- централізовано контролювати canvas;
- підключити API та БД без перебудови frontend-архітектури.
